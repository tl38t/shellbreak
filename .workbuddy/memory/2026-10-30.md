## 二、「用云端覆盖本地」无效（玩家真机诊断，本轮修）

玩家现场：local 第 1 周目 · 4 分钟（15 秒前保存），cloud 第 1 周目 · 22h54m（16 小时前备份），
诊断同时出现 `错误 后台原生文件同步保存未确认` 与 `写盘 失败=0`。

### 根因（三条证据自洽，不是猜）

1. 那条错误**只**由 `flushNativeSync()` 返回 false 时写入（game.js 的 `tap.onHide`）。
2. 「写盘 失败=0」⇒ 不是写失败（`flushNativeSync` 的 catch 会 `st.fileFail++`）⇒ 只能是早退。
3. `nativeLatest` 不可能为空（`state.js:1015` 每次 saveRun 都调 `writeNativeSave`，本机 43 次成功）。
⇒ 只剩 `typeof fs.writeFileSync !== 'function'` 那条早退 ⇒ **该设备的 FileSystemManager 没有
同步读写方法**（异步 `writeFile` 正常，所以异步落盘 43 次全成功）。

后果两条：
- `installImportedSave` 里「原生同步写必须确认」的**硬门槛恒 false** ⇒ 回滚 + throw ⇒
  「云端覆盖 / 存档码导入 / 文件导入」三条救援路全废，玩家只觉得「按钮没反应」。
- onHide 那一份从未落盘 ⇒ 切后台/杀进程时最后一段进度只挂在异步队列（JS 随时被冻结）。

### 这道门槛是 1.0.5 引入的（不是老问题）

`git log -S "原生文件未确认写入，导入已中止"` 只有两条：`c72fc778`（Ver1.0.5 引入）与本轮
`b6e29571`（删除）。**1.0.4 及之前 `installImportedSave` 写完 localStorage、读回校验通过就
`reload()`，完全不碰原生槽** ⇒ 任何机型都能导入。玩家说「以前可以载入云存档」是真的。

⚠️ **两条救档路不同源，必须分开看**：
- **启动自动恢复** `restoreFromCloudIfAny` → `adoptBundle`（10-28 P0 起就不借 installImportedSave），
  **只在 `decideRun` 判「本机三处全空」时才触发**。
- **面板「用云端覆盖本地」/ 存档码 / 文件导入** → `installImportedSave`（1.0.5 起带门槛）。

⇒ 本机有档时（哪怕是被顶出来的 4 分钟新档），**自动路不触发、手动路被门槛挡死**，
云端好档就那样摆着进不来。这才是「按钮没反应」的完整解释，也是为什么「别人能用他不能」。

### 门槛判据错在哪（三格两种活、一种死）

`fsAvailable()` 只问「有没有 `getFileSystemManager` + `USER_DATA_PATH`」，
`writeNativeSaveSync` 还要「有没有 `writeFileSync`」—— 两件事不等价：

| 能力组合 | 谁在这格 | 结果 |
|---|---|---|
| `fs=0` | 纯浏览器 / 容器不给文件系统 | 外层 if 跳过 ⇒ **成功**（等同 1.0.4） |
| `fs=1, wfs=1` | 主流机型 | 门槛通过 ⇒ **成功** |
| `fs=1, wfs=0` | **该玩家**（诊断 `能力 ls1ts0fs1cl1` 的 fs1 即铁证） | 进门槛 → 内部早退 ⇒ **回滚 + throw** |

⚠️ 1.0.5 加门槛的动机是**对的**：导入后要 reload，若不同步写原生槽，重启时三源扫描会读到
旧原生快照（seq 更大）把导入档盖回去 —— 即「导完重启又变回新档」。
⇒ 所以 1.0.7 必须「删门槛 + 打新 `_saveSeq`」**两条配套**，只删门槛仍会被旧快照赢回去。

### 修复（5 条）

1. `flushNativeSync()` 补 `tap.setStorageSync` 同步兜底（官方明写「长期保留」，1MB/键、总 10MB，
   本档 ~8KB）。落点是**主键本身**（`CFG.SAVE_KEY` / `CFG.RUN_KEY`）——启动扫描的 tapStorage
   分支读的就是这两个键，不必加第三套逻辑。`nativeHold` 期间仍然一律不写。
2. `writeNativeSaveSync` 去掉 `fsAvailable()` 前置（否则 kv 退路一起被掐）。
3. `installImportedSave` 删除原生写硬门槛：localStorage 写后读回通过即放行，原生改
   「同步 → 异步(forceNew) + mirrorWrite」尽力而为，不再整单回滚。
4. 新增 `stampFreshSeq()`：导入/接管时给 run 打**本机最大** `_saveSeq`。云档带的是来源设备的号，
   不换就会输给刚把旧档顶掉的那个新档（=「导完重启又变回新档」）。
5. 「用云端覆盖本地」改走 `adoptBundle` **就地接管**（不 reload、不过门槛），覆盖前
   `backupLocalNow()` 兑现面板「会先备份本机」的承诺。

诊断新增一行 `落盘 同步=file|kv|nosync|nolatest|hold`，下次一眼定性。

### 回归

`sim/e2e-suites/boot-gate.mjs` 新增 G 段 8 条（无同步文件 API 设备上的落盘与导入）。
**1270 ✓ / 106 ✗ × 3 连跑零漂移**，106 条与干净 worktree 基线逐条相同

### 夹具坑（新，写新套件必看）

伪 DOM 的 `setTimeout` **不认延迟**：boot 同步跑完 scan 就 `__flush`，会把 `bounded(…, 2500)`
的超时定时器**当场**触发 ⇒ 扫描被判 `uncertain` ⇒ 直接崩在 `showRecoveryPending`。
⇒ 夹具里必须 `await sleep(0)` 让微任务先落定，再开始 flush。

### 第三条：`writeNativeSave` 同样被门槛掐死（写能力矩阵夹具时当场抓到）

造「只有 kv、没有文件系统」那一格时发现：`writeNativeSave` 开头
`if (nativeHold || !fsAvailable() || …) return` ⇒ 这类机器上 `nativeLatest` **恒为 null**
⇒ `flushNativeSync` 只能返回 `nolatest` ⇒ **kv 兜底一次都不触发**。
与导入被掐是同一个病：**前置门槛把兜底和主路一起掐死了**。
已改为「无 fs 但 `syncStorageAvailable()` ⇒ 只留快照，交给 `flushNativeSync` 同步写」。
⚠️ 无 fs 时**不能**进 `writeNativeNext`（它直调 `getFileSystemManager()`，会 TypeError）。

### 诊断新增「接口」一行（`shapeText`）

`能力 ls1ts0fs1cl1` 只回答「有没有这条通道」（`fsAvailable()` 只查
`typeof getFileSystemManager === 'function'` + `env.USER_DATA_PATH`），新行
`接口 wfs1 rfs1 wf1 ud1 kv1` 回答「这条通道能做什么」。**本次事故正长在两者之间**（fs=1 但 wfs=0）。
**实时探测而不是存盘**：能力是「此刻」的事实，存下来只会留下上次启动的旧样子。

### 能力矩阵（夹具的结构性补强）

四格各一套：全有 / 有 fs 无同步（G）/ 只有 kv（H）/ 无 tap（F）。
今后任何「行为依赖某个 API 存在」的代码，都必须在这四格里说得通 —— 只测 happy path 等于没测。
