## 09:10 存档调研：同类游戏怎么做的（玩家仍在报掉档）

## 09:30 实装：启动云端救援 + 防覆盖守卫（用户确认真机云存档走通）

**先纠正我 09:10 那条的错误**：自动云备份**早就做完了**（`save-transfer.js` 的 `pushCloud(silent)` + `AUTO_GAP_MS=5min` + `boot()` 里 30s `setInterval(autoCloudPump)`，2026-10-27 那批）。我当时只 grep 了 `setInterval|setTimeout` 就断言「无自动备份」，属于没读全就下结论。

真正的两个洞（本次实装）：
1. **启动恢复链不看云**：`state.recoverAsync` 只回查本机 `tap.setStorage` + `tapfile://usr`。本机三层同生共死 ⇒ 清缓存/换设备即三处同时消失 ⇒ 判新玩家开新档。
2. **新档反过来顶掉云端**：开新档 30 秒后 `autoCloudPump` 就把「0 分钟新档」`updateArchive` 上去，把云端真档覆盖 —— 唯一能救回来的备份被自己删了。这才是「玩家还在说掉档」的完整闭环。

落点：
- `save-transfer.js` 新增 `restoreFromCloudIfAny(cb)`：`findOurArchive` → `getArchiveData` → `readFile` → `validateBundle` → `SB.game.installImportedSave(bundle)`（内部 reload，走已验路径）。8s 超时；`shellbreak.cloud-recover-at.v1` 60s 内只试一次。`cloudAvailable` 一并导出。
- `game.js` boot 的 empty 分支插入「第四路」：本机三处全空 → 问云 → 命中则 reload 接管 → 都没有/超时才 `startRun()`。**只在原本已走异步的那条分支里插**，浏览器与 e2e 沙箱仍走同步 `startRun`，行为零变化。
- `pushCloud` 加防覆盖守卫：**只拦 silent（自动）**，云端 `playtime ≥ 600s` 且 `本地×3 ≤ 云端` ⇒ 跳过并记 lastError；手动上传放行。

## 09:52 对照官方 API 文档逐项核对云存档实现（用户要求）

核对源：`cloud-save-tutorial`（接入指南）+ `CloudSaveManager.getArchiveList` + `CloudSaveManager.createArchive` 三个官方页。

**结论：调用方式全部写对，但查出两个真 bug（已修）。**

✅ 对的部分：`tap.getCloudSaveManager()` / `getFileSystemManager()` / `tap.env.USER_DATA_PATH`；`fs.writeFile({filePath,data,encoding:'utf8'})`；`getArchiveList → res.saves`（顶层字段 `uuid/fileId/name/summary/extra/playtime/saveSize/modifiedTime/createdTime`）；`getArchiveData({archiveUUID,archiveFileId,targetFilePath}) → res.filePath`；`readFile → data`；`createArchive({archiveMetaData:{name,summary,playtime,extra}, archiveFilePath})`。存档名 `shellbreak_main` 无空格无汉字、15 字节 < 60 ✓；summary 非空 ✓；playtime ≥ 0 ✓；extra < 1000B ✓；先 writeFile 后 createArchive 的顺序正确 ✓；`updateArchive` 会改 fileId 而我们每次现查列表、不缓存旧 fileId ✓。

⚠️ **Bug A（致命但当前无感）**：`findOurArchive` 的排序写的是 `updatedAt || modifyTime || createdAt` —— 官方字段是 **`modifiedTime` / `createdTime`（秒级）**，三个全不匹配 ⇒ 恒为 0 ⇒ 排序完全失效。单槽看不出，P1 多槽会把最旧的当最新下载。已修（保留旧名做前向兼容）。
⚠️ **Bug B（边界）**：手动上传冷却 60000ms，官方明写「createArchive 和 updateArchive **一分钟之内最多调用一次**」⇒ 60.0s 卡边界，平台很可能仍判 400001。改 **70000ms**。

**另外两处口径澄清**：① 官方小游戏接入指南的频次是「每分钟 1 次」（MCP 工具指南写的「60 次/分钟」与官方功能页的另一套限制不是同一条，按更严的来）；② `400006 非法的操作令牌`（网络抖动/耗时过长）是可重试错误，当前只显示消息、未自动重试。

**验证**（`tmp/_cdp_cloudfields.mjs`，mock 两个同名档 OLD(modifiedTime=1000) / NEW(modifiedTime=9999999)）：`updateArchive` 收到 `uuid=NEW` ✓；紧接着手动上传被 `COOLDOWN: …请约 70 秒后重试` 挡住 ✓。bump `save-transfer.js?v=4`。

## 09:58 取证：跨设备「旧档覆盖新档」漏洞仍在（未修，待拍）

- `tmp/_cdp_cloudoverwrite.mjs` 实测：mock 云端 = 5 小时、本地 `s.t = 10800`（3 小时），调 `pushCloud(true)` ⇒ **`UPLOADED`，走 `updateArchive`，云端 5h 被 3h 覆盖**。
- 根因：现有防覆盖守卫的判断是「云端 ≥ 600s **且** 本地×3 ≤ 云端」，只能拦「云端 ≫ 本地」（10 倍量级）。3h vs 5h 这种**同量级倒退**完全拦不住。
- 真实场景：手机 A 玩到 5h（云端 5h）→ 换手机 B（本地存着 3h 旧档）→ 启动只读本地、不查云 → 30 秒后自动上传 3h → 云端 5h 没了 → 回手机 A 也变 3h。
- 建议修法（两行）：自动上传加「不允许倒退」——`云端 playtime > 本地 + 60s` 即跳过（手动上传仍放行）。比现有 ×3 守卫更严、更符合直觉。
- 用户另提需求：本地与云端不吻合时**让玩家自己选**用哪份（未实装，已给 A/B 两案）。
