## 玩家截图诊断：「离线结算了但恢复的档不对」

**结论：离线补算没算错，是那份档本身就只有 108 秒。** 用截图数字反推整条链：

| 项 | 数值 | 推导 |
|---|---|---|
| 恢复提示 | 0.03 小时 / 壳厚 499988 | t=108s，已削 12 |
| 现在 | 存续 0.43 小时 / 已削壳 162 / 壳厚还剩 499838 | 500000−499838=162 ✓ |
| 离线 | 23 分 8 秒 = 1388s | 0.03h + 0.386h ≈ 0.43h ✓ |
| 离线削壳 | 162 − 12 = 150 | 1388s × 0.108/s ✓ |

⇒ 时间、壳厚、削壳量三者互相闭合，**离线区间确实被补进去了**。
⇒ 真正现象是「恢复的档 = 一份 108 秒龄的新档」：巢穴 0 级、资源 0、人口 0，符合 «108 秒还没攒够 5 珊瑚» 的开局态。
⇒ 也就是说：**存档在更早就已经不是原来那份了**，离线结算只是把它继续跑下去。

## ★★ 玩家「退出就没存档」根因定性：**只用了沙盒不保证的那条存储通道**

用户问「是不是受 TapTap 沙盒影响」。查官方一手文档后结论：**是，但不是"被沙盒影响"，
而是我们 100% 依赖 `localStorage`，而 localStorage 在小游戏容器里官方从不承诺持久。**

### 证据链（全部来自 TapTap 官方一手资料）

1. **我们的实现**：存档读写全在 `localStorage`（`state.js` 8 处、`game.js` 26 处）。
   `tap.setStorage` / `getStorage` **一次都没用过**；`tap.env.USER_DATA_PATH` 只在云存档上传时当中转目录。
2. **官方把小游戏的"持久化"明确标在 tapfile 上**：云存档文档的文件路径协议表里，
   `tap.env.USER_DATA_PATH` = `tapfile://usr` 标注「**用户数据目录（持久化）**」，
   `TEMP_DATA_PATH` 标「临时文件目录」，`STORE_DATA_PATH` 标「存储目录」——只有 usr 被称持久化。
3. **`tap.setStorage` 官方承诺持久**：「数据将被保存到本地缓存的指定键名中……存储的数据将**长期保留**，
   除非用户手动删除或系统因空间不足自动清理。每个键 1MB，总计 10MB。」
   —— 注意它是**独立于浏览器 localStorage 的 TapTap 通道**。
4. **官方社区文章（TapTap 制造 / WASM 模式）原话**：
   「本地存储依赖浏览器 IndexedDB，清缓存或换设备就会丢失。所以云存档不是可选项，而是必须。」
   「WASM 的本地存储既不可靠也不跨设备。」
5. **同类上线小游戏的实做（app 976396《维修物语测试》存档说明）= 行业标准**：
   本机**三处**（浏览器缓存 + `tap.setStorage/getStorage` + `USER_DATA_PATH/wx_local.json`）
   + 云存档（1 份**自动备份**，进度变化后**每分钟最多上传一次**，始终更新同一份 + 3 个手动槽）。
   「开门时优先使用本机存档，**本机三处都没有时才读取云端**；
   **本机或云端没有回应时不会自动开新档**，会在加载页等待并提供「先开新档玩着」按钮。」

### 我们 vs 行业做法

| 维度 | 壳（现状） | 行业做法 |
|---|---|---|
| 本机持久化 | **只有 localStorage 一处** | localStorage + `tap.setStorage` + `tapfile://usr/xx.json` 三处 |
| 云备份 | rc18 之前纯手动；rc18 起 5 分钟节流自动 | 自动，**1 分钟**节流 |
| **读不到时** | **静默 `startRun()` 开新档，并立刻 saveRun 覆盖** | 不自动开新档，加载页等待 + 「先开新档玩着」按钮 |

⇒ **最后一行才是「存档没了」最可能的直接机制**：容器清了 localStorage 或读失败 →
`loadRun` 返回 null → `boot` 走 `startRun()` → `game.js:188` 立刻落盘 → 旧数据被新档覆盖。
玩家看到的不是"存档丢了"，而是"变成新档了"（与截图里 `已恢复上次进度：0.03 小时` 完全吻合）。

### 待拍板的修复方案（架构级，改存档核心，须用户确认）

**P0（直接治"退出就没存档"）**
1. 存档层抽成多后端：写 = localStorage + `tap.setStorage`（小游戏环境）；
   读 = 三处取 `_ts` 最新的那份。单 key 1MB / 总 10MB 足够（满配档仅 7.6KB）。
2. `tapfile://usr/shellbreak-save.json` 作第三处（更耐久，且可直接喂给云存档，省一次中转写）。
3. **改掉静默开新档**：`loadRun` 返回 null 时先尝试 `tap.getStorage` / 文件；
   全都拿不到再进"加载页等待"而不是直接 `startRun()`（至少开新档前把残留备份留全）。

**P1**：自动云备份间隔 5 分钟 → 1 分钟（对齐行业做法）；清档/覆盖前确认云端有份。
