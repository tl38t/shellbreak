## 离线补算性能诊断（用户问「为什么离线计算这么慢」）——只测量未改代码
- 新建 `sim/perf-offline.mjs`（loadNoDom + civics/companies 补载，造晚期局状态实测）：
  - `economy.tick` **38.5 µs/tick**（晚期局·桌面 Node；逐项拆账无单一元凶——foodRate+foodUse 3.1µs、tickShell 1.6µs、tech.mul 1.0µs、cultureRate 1.05µs ×2 次/tick（1526/1529 两行，可省一次）、globalMul 0.49µs，其余为 30+ 产出/生死/加工行的均摊成本）。
  - tech.pump 5µs + civic.pump 10µs/拍（晚期大头被 eurekaMet 永久台账缓存；未达成 rate 类科技每拍重跑 rates()=24µs，占小头 0.4s）。
- **8h 满档离线推算**：1× = 288,000 tick → 纯算 11.5s；2× 广告全程覆盖 = 576,000 tick → 纯算 22.6s。
  **墙钟 = 纯算 ÷ 占空比**（CATCHUP_BUDGET=50ms / 100ms 帧 = 50%）⇒ **桌面 23s / 45s**；TapTap 手机 webview JS 比 Node 慢 3-10× ⇒ 手机实际 **2-7 分钟**——这是「体感慢」的主因。
- 结构成因（代码注释实证）：① 离线 = 逐 tick 回放同一条 economy.tick（「同路径」纪律，保证与在线逐位一致）；② adMul=2 使每真实秒 tick 数翻倍（开 2× 反而让补算更慢，反直觉）；③ 50% 占空比分帧（game.js:551 注释自述 50 是「保守占位」，当初 8 时曾 12.5× 墙钟）。
- 优化选项（**结构改动待用户拍板，未动手**）：
  - A（最便宜）：CATCHUP_BUDGET 50→90（占空比 90%）⇒ 墙钟 ÷1.8（45→25s）。补算期间界面被离线闸门 modal 锁死、无需交互响应，50 当年是保守占位。改 1 常数 + 回归。
  - B（激进）：乘区稳定段批量合并 tick（一次 addRes 覆盖 N tick）⇒ 纯算 5-10×，但需证明与逐 tick 逐位一致，动核心结算路径，风险高。
  - C（否决项）：离线用 dt=0.2 跑 10 tick/秒——改变离散近似粒度（生育/冻死判定），违反「同路径可复现」，不建议。
- 遗留小优化点：tick 内 cultureRate(s) 被调两次（1526 与 1529 行），可合并省 1µs/tick（约 3%）。
