## 三、UI / 断言 / 渲染反模式

- ⚠️ **`SB.game.render()` 是脏标记门控的**（`game.js:126` `if (dirty)`）：测试里连着调两次

### ⚠️ 2026-09-28：一处少括号，把整条资源线的容量打成了 0

**现象**：`--balance` 报「单局 0.00h」、`runHours` 恒 0；e2e 15 项珊瑚链全红；
手动点 600 下「采珊瑚」仍攒到 0.0（需 10）。

**根因**（`src/economy.js` 的 `capOf`，我上轮加奇观仓储时写成）：

```js
return base + (s.lvl.ballast || 0) * BLD.ballastCap +
  SB.wonder ? SB.wonder.matMaxBonus(s, k) : 0;   // ← 少了括号
```

`+` 的优先级高于 `?:` ⇒ 它被解析成 `(base + ballast*cap + SB.wonder) ? bonus : 0`
—— **左半边整个变成条件，返回值只剩三元那一项**。
⇒ `capOf` 对一切非 kelp 资源恒等于「奇观加成」（0 或 200），`CAP_BASE` 与压舱仓全被丢掉。
实测：`capOf(kelp)=200` 对，`capOf(coral)=0`、`capOf(stone)=0` ⇒ 珊瑚/石头/金属/精铁
**全都存不进去** ⇒ bot 跑不穿整局 ⇒ 所有时长数字都是 0。

**为什么断言没抓住**（两条，都要记住）：
1. 石梁那条测的是 `stoneBeam`——它走 `CAP_BASE` 无键 ⇒ `Infinity` 路径，**压根没碰这条 return**；
2. 「仓储加成 +200」比的是**差值**，两边一起错时差值照样成立 ⇒ 假绿。
   ⇒ **判据：凡是「表 + 加成」形状的函数，必须逐键钉绝对值，不能只比差值。**
   已补断言「每种材料的容量都拿得到 CAP_BASE」。

**取证顺序（这次的弯路，下次直接走）**：
`直接调 addRes` → `同 state` → `capOf 各资源` → **把函数体 `toString()` 打印出来** → 看 return 那行。
⚠️ 前四步全都在「推理」，只有打印 `toString()` 才是**看着真实执行的那行代码**。
这次卡在第五条才看见 `+` 和 `?:` 的优先级之争。
⚠️ `capOf.toString().slice(0,300)` **会把 return 截掉**——函数不是从开头到某个点结束的，
截断有可能正好切掉出问题的那几行。**打印全文。**

### ⚠️ 2026-09-28：**墙钟没被钉住**，量具本身在抖（钉随机源不够）

**现象**：钉了 `SB.rng` 之后，同一个仓库连跑三次，整局 **8.49h / 9.69h / 9.97h**，
整棵树 **8.02h / 8.92h / 8.69h**。**同代码、同种子，差 1.5h**——比上次那条还难查，
因为随机数看起来已经「修好了」。

**根因在 `src/game.js` 的 `loop()`**：每帧做两件独立的事——
`var wall = Date.now()` 算 `gap = wall - loop._lastWall`，而 `gap >= CFG.OFFLINE_MIN`
时会调 `planCatchUp` ⇒ 进去是 `drainCatchUp(预算)`，
**那个 while 循环的条件是 `Date.now() - t0 < budgetMs`——墙钟预算**。

sandbox 里 `performance.now` 传的是 `fakeNow`（跟着 `frames()` 一起走），
但 `Date` 传的是**真实 Date**。于是 e2e 跑得越快 gap 越小、越慢就越大，
**离线补算的迭代次数直接由机器负载决定**。这不是误差，是量具 itself 在抖。

**判据（一句话）**：**随机源只是一条输入。时钟是另一条。** 核算前先把
`Date.now` 也接到 `fakeNow` 上（sandbox 里塞一个 `new Proxy(Date, {get:(t,k)=> k==='now'?(()=>fakeNow):t[k]})`），
否则「可复现」只是假象——种子钉住了，机器负载还在顶。
⚠️ ⚠️ 这条**不要擅自加进 e2e**：核算段是用户的活，量具改不动手，等他发话。

## 五点六、全资源产出乘区 `globalMul`（2026-09-28 灯塔上线，四条判据）

1. **`globalMul` 与 `gatherMul` 不是一回事，别合并。** gatherMul 是**采集**倍率，只罩
   珊瑚/石头/金属/暖石四种职业采集物；「全资源 +1%」罩的是**进资源池的每一条产出行**。
   合并的后果是「面板写了 +1%，实际只有四种资源吃到了」。
   **覆盖清单**（新增一种资源进池时必须同步加，漏了不报错不 NaN，只是它静默不吃加成）：
   珊瑚·石头·金属·暖石·精铁·科技·地热·藻食·市政点。
   **例外只有两处，都是有意的**：① 口粮消耗 `foodUse` 不乘（消耗不是产出）；
   ② 精铁的 `fc` —— 乘，但「扣原料那一份」不乘（灯塔不该让玩家少扣一份料）。
2. **乘区宿主 `wonder.globalBonus()` 必须是空实现但存在。** 它现在没有奇观用这个键，
   但留着 = 把「奇观给全资源产出」那条通道事先接通；等将来加键时再补实现，
   就会重演「数据写了实现层没读」的静默断链。
3. **造测试 state 的三个坑**（本轮四条断言全是假红才逼出来的）：
   ① `jobs` / `lvl` 一律 `Object.assign` 打补丁，**禁止整体替换** —— 替换会顺手删掉
      `lvl.reef` 之类没写在字面量里的键，而 `gatherMul` 会读它 ⇒ `undefined * 0.08 = NaN`
      ⇒ 四条采集物静默 NaN；
   ② `frozen` 要显式解掉，冰封期 `cold=0`，产出恒 0 ⇒ 比值无从比；
   ③ 库存初值必须**低于仓储上限**（silt 基础上限 200，填 500 会被 `addRes` 夹回去，
      那一 tick 的主导量变成「削减库存」而不是「产出」，比值完全失真）。
4. **验净额时的「毛额」口径**：silt / warmstone 的 `rates` 是**净额**，末尾减了**未放大**的
   `fc`。补回去的那份必须是**未放大的 fc**（= A 组 iron），拿 `r1.iron`（已 ×1.01）去补
   会重复计价，把正确的 1.010000 虚报成 1.012222 —— **红是假的，会把排查方向带歪**。
   同理，地热那条：灯塔自己也是建筑，升一级会把 `lvlSum` 抬高 ⇒ 城邦维护多 `BLD.upkeep`
   一份也不放大，严格等式是 `fuelRate(B) === (fuelRate(A) − BLD.upkeep) × gm`，
   写成「增量 = 1% × 净额」会红（差 0.0015×gm）。
   ⚠️ 这类「假红」比「不红」更危险：它让人以为产品代码漏乘，去改根本没坏的那一行。

## 五点七、era2 第三层（工程学 / 数学 / 构架术）并存的四种断链（2026-09-28）

三条新科技同时开的三条新通道（配方解锁门、仓储乘区、工坊效率加区），
一次暴露出**四种**「不报错但等于没做」。改任何一条新轴之前都先读这节。

1. **`freshRun` 的 `res` 字面量漏键 ⇒ 产物变 NaN（不报错）**
   加资源只往 `SB.RESS` 加条目、没改 `state.js` 里那行手写字面量 ⇒
   `res.ironBracket === undefined` ⇒ `addRes` 里 `undefined + 5.25 = NaN` ⇒
   `Math.min(Infinity, NaN)` **还是 NaN** ⇒ 产物进了池子却读出来是 NaN，
   面板显示「NaN 铁制支架」，升级项扣费 `undefined - 50` 又把池子整个污染。
   **修了两层**：字面量补齐（`state.js` 已经为 stone/warmstone/culture/stoneBeam
   各写过一次同样的注）+ `addRes` 兜底（**只把非数字洗成 0，NaN 原样留下**——
   NaN 的 typeof 就是 'number'，这层拦不住它，于是它会一路红到断言上；
   把 NaN 也洗成 0，就等于同时藏住「变 0」和「变 NaN」两种事故）。
   **判据**：`freshRun().res` 的键必须覆盖 `SB.RESS`，已有常驻断言盯着（缺一个必红）。

2. **同一个量被写了两遍 ⇒ 台账翻倍**
   `craft()` 在调用端又补了一句 `s.got[c.res] += gain`，而 `addRes` 内部已经写过一次
   ⇒ 工艺制品的累计产出**记了两遍**（实测造一次得 5.25，台账上是 10.5）。
   `s.got` 正是 `{t:'gathered'}` 尤里卡条件的读端 ⇒ 造 100 条石梁会点亮「累计产出 200」，
   **不报错，就是错**。**判据：一个量只该有一个写点**，别在调用方再补一笔。

3. **加区键进了 `mul()` 却没人读**
   `mul()` 老老实实把 `craftRatio: 0.05` 算进了 `T.craftRatio`，面板也照着显示
   「工艺制作效率 +5%」，但 `workshop.craftRatio()` 那两个来源（工坊等级、奇观）
   **压根没有第三条** ⇒ 研究完什么都没发生。**与 `BLD.workshopCraft` 那次同型**。
   **判据：每加一个 effect 键，先回答「谁在读它」**；答不上来就是还没接线。

4. **系数通了、功能却没入口（本次最隐蔽的一条）**
   `capOf` 那条 `upg_ballast_1` 的 ×1.5 早就是通的、e2e 也绿，但工坊面板上
   **根本没这一块**——玩家点不到，×1.5 等于不存在。缺的是**入口**不是实现。
   **判据：点不到的效果等于没做。**
   ⚠️ 这条与 §三 的「UI 断言」不是一回事：那些是「面板要跟着状态翻」，
   这条是「**一块内容整个缺席**，e2e 只看数据层时完全看不出来」。

**附：断言自己算错量纲（不是实现错）。** 那条「造铁制支架」的断言原本拿
`20 - gain`（产出 5.25）去比铁的余额（投入扣 5 ⇒ 实际 15），永远不成立，
而代码从头到尾是对的。**改常数让断言绿 = 标定（停）；断言比错量 = 量错了（修）.**
分界是「错的那一方是谁」——先确认实现对不对，再动断言。

## 五点八、市政侧两条新解锁轴（对外贸易 / 戏剧与诗歌，2026-09-28）

era2 第一层把「解锁权」第一次放到市政身上（此前的解锁权全在科技侧），
连带出**五条**「不报错就是错」。改 `requiredCivic` / 职业 `job` / 市政 `card` 前先读这节。

1. **建筑解锁轴从 3 条变 4 条，首行守卫必须一起认**
   `habitat.unlocked()` 首行是「没声明任何条件 ⇒ 默认锁着」（漏写等于忘了决定）。
   新轴 `requiredCivic` 若不并进那一行，挂着市政声明的广场会被**首行直接挡死**——
   与 `e2e`「无任何解锁声明」那条断言的道理完全一样，所以断言也要同步认这一轴。
   **判据：每加一条解锁轴，同时改三处** —— `unlocked()` 首行、`unlocked()` 判定、
   `lockReason()` 报因（顺序：纪元 → 科技 → 市政 → 资源，理由要玩家当下可执行）。

2. **`jobUnlocked` 写 `return !cid || ...` 会一次放出 6/7 个职业**
   原语义是「**两边都没声明 ⇒ 永远解锁**」（珊瑚匠这类本来无条件可雇）。
   写成 `!cid` 短路 ⇒ 「凡不挂市政的职业全无条件解锁」⇒ 连默认夹具态都变了。
   正确形状：`if (cid) return !!s.civics[cid]; return !tid;`。
   **判据：反查表为空 ≠ 该职业没人管**，别把「查不到」当成「放行」。

3. **`freshRun` 的 `lvl` 字面量同时是 `migrateRun` 里 `fixTable` 的 ref**
   `fixTable` 按 **ref 的键**遍历 ⇒ 表里没有的建筑 id，**读档时整条被丢掉**。
   实测：建起广场 → 存档 → 刷新 ⇒ 广场等级静默归零，不报错、症状只有「它没了」。
   本轮一次抓到两个（`institute` 早就漏了，`square` 是新漏的），
   外加 `lighthouse`（它有 `s.lvl.lighthouse` 三个读取点）。**与 civics 那次同源**。
   **判据：`base.lvl` 的键集合 == `SB.BUILDINGS` 的 id 集合**，已有正反两条常驻断言。

4. **比对乘区时要先把乘区外面那部分减掉**
   广场乘区只裹「书手那一项」，议事厅（`lvl.hall × HALL_RATE`）在乘区**外面**。
   拿 `cultureRate(装卡) / cultureRate(不装)` 直接比 ⇒ 得到 1.94 而不是 2
   （议事厅那份没被放大），而**实现从头到尾是对的**。见 §五点七 附条同型。
   **判据：算比值前先问「这一项在不在括号里」**；拿全值比 = 自己造一个假红。

5. **「有没有效果」不能只判 `effect` 非空**
   `sim/e2e.mjs` 的 bot 装卡判据是「`effect` 非空」（《技艺》是空壳，装它白占槽）。
   政策卡《戏剧与诗歌》的 `effect` **同样是空壳、却挂着 `squareMul` 乘区** ⇒
   按旧判据 bot 永远装不上它，广场那条线整局不生效而回归全绿。
   **判据：有没有效果 = `effect` 的键 **或** 任何乘区字段**（`squareMul` 等）。

**附：加条件类型必须成对补 `condMet` + `condShort`。**
「建成一座奇观」此前 12 种类型里都没有，只写 `boost:{t:'wonder'}` 会
**静默永远达不成**（不报错、不红）；补了 `condMet` 忘了 `condShort`，
面板会印出 `undefined.txt`。两处是同一条契约的两端，别只补一头。

**附：本轮新开的覆盖洞（2026-09-28 已拍板并堵上，留档备查）。**
`sim/e2e.mjs` 的 `wantBuild()` 里**没有任何奇观** ⇒ bot 整局不建奇观 ⇒
「建成一座奇观」永不成真 ⇒《戏剧与诗歌》永远研究不了 ⇒ 广场整局不被建、不生效，
而 **412/412 照样全绿**。真人玩家能建（石工解锁海潮方碑），所以是覆盖洞不是死锁。
用户拍「两档都做」：① 补真实路径断言（不动时长）② 把奇观看情形接进 bot 流程。
⇒ 已接，回归 **418/418**；单局时长的扰动**未读、未调**（属标定，等用户对账）。

## 五点九、整局模拟的 bot 行为清单 = 断言覆盖面的真实指示（2026-09-28）

**判据一：「宣布 X 已发生」的夹具断言不算覆盖。**
凡是用 `s.wonders[id] = true` 这类**直接摆状态**通过的断言，会把全部门槛
（科技 / 材料 / 时间）跳过 —— 它证明的是「给了就生效」，不是「给不给得了」。
⇒ 每补一条正面断言，都要配一条**否定侧**：不给时建不成，且**说得出为什么**。
   拦阻函数的文案是可断言面：`wonderBlocked` 没科技时必为 `需要先研究「X」`、
   缺料时必以 `还缺` 开头并带 `缺多少（现有 n）` —— 少了这几条，
   「石梁写了 20 实际扣 18」这类错会静默溜过。

**判据二：不同入口的东西，不能塞进同一张建造清单。**
`wantBuild()` 的返回值会经 `clickBuild()` 点 `data-build`，而它拿 **`s.lvl[id]`** 判成功。
⇒ 一切**没有等级**的东西（奇观、工具、工艺制品）塞进去都只会得到
   「点了没反应」——`lvl[id]` 恒 `undefined`，且会 `break` 掉整个建造循环。
   奇观走 `data-wonder`、石梁走 `data-craft`，必须各自单独接一条通道，
   成功判据用各自的真实字段（`s.wonders[id]` / `s.res.stoneBeam`），别复用 `lvl`。

**判据三：里程碑类只此一次的东西，要排在 bot 策略的前面。**
排在普通建筑之后 ⇒ bot 永远有更便宜的可建，永远轮不到它。
（本轮实证：海潮方碑排在第二优先级时，bot 连石梁都不造 ⇒ `stoneBeam` 整局恒 0
 ⇒ 奇观、大灯塔、研究所三条线的**材料来源**都没被跑过。）

**判据四：「整局跑完后 X 真的发生了」比「各处断言都绿」更值钱。**
放在整局之后的那一条，是唯一能证明「这条链物理上走得通」的地方 ——
连「bot 到底攒不攒得出材料」这种纯数值问题也一并验了。
⚠️ 它红了 ⇒ 先分清两种，别急着改设计：**bot 策略上排不上**（改顺序，属覆盖）vs
**门槛根本攒不出**（改数值，属标定，停下等拍）。海潮方碑的真实门槛 =
石工 + 20 石梁（≈2000 石头）+ 300 珊瑚，量级不小，正是这类分界的高发区。

## 五点十、era2 第二层（神学 / 历史记录 / 神庙 / 大图书馆，2026-09-28）

**判据一：「效果翻倍」有两种读法，数字差得很远 —— 它必须有唯一的裁判。**
「图书馆效果翻倍」可以读成 (a) 图书馆那一截 ×2、(b) 整条科技产出 ×2。
用户拍的是 (a)。⇒ 乘区只能裹 `(1 + 图书馆等级 × sciRatio)` 这一截，
**研究所那份留在括号外**。纯图书馆情形下的总比值不是 2 而是
`(1+2×0.1×2)/(1+2×0.1) = 7/6 ≈ 1.1667`；只有带上研究所时比值才会进一步回落到
`(1+2×0.1×2+instSci)/(1+2×0.1+instSci)`。
⚠️ 这两条断言是「翻的是那一截不是那一条」这句话**唯一**的执行者：
改乘区位置之前先回来读这一段，否则「整条 ×2」会悄悄回来，而界面上没有任何提示。

**判据二：「装前 / 装后」必须是两个独立 fixture。**
在同一个对象上切卡，会因为**断言参数从左到右求值**而自相矛盾 ——
条件里先把卡装上去，同一条 `check` 的 `detail`（以及后面那次 `rates()`）读到的
已经是装卡态，症状是「比值恒 1、`libraryMul` 装前也报 2」这种谁也看不懂的输出。
⚠️ **2026-09-29 复现（马具实装）**：同一坑的另一种落法 —— 条件里的布尔值
（`canBuy`）是在夹具**中段**取的，取完科技才还回去 ⇒ 断言执行时它测的已是
「研究后」的世界 ⇒ 假红。判据二推广一步：**凡夹具中段取的标量，取的时点就是它的世界**，
要么取完立刻用，要么换名区分前后两态。

**判据三：虚级的落点是 `costOf`，不是 `s.lvl`。**
「只加效果、不提高建筑所需材料」在代码里的唯一落点 = `costOf` 读 `s.lvl[id]`。
⇒ 断言 `costOf(gWon,'library')` 与 `costOf(gLib,'library')` **逐字节相同**，
一条断言同时证明「没写进 `s.lvl`」和「没影响成本」。
⚠️ 一旦虚级落进 `s.lvl`，会被 `lvlSum`/`need`/`costOf` 一并读走，
玩家会看到「还差 1 级就能建，而那一级早就白送了」。

**判据四（新覆盖洞，待拍）：bot 的凿料阈值写死，会把里程碑饿死。**
2026-09-28 实测：`wantBeam()` 的门槛是硬写的 `< 20`（海潮方碑的标价）。
bot 花完那 20 根就不再凿 ⇒ **大图书馆永远差 5 根**（它要 25），
于是「大图书馆 + 虚级 +3 + 一次性 1000 科技点 + 《历史记录》乘区」整条链
在整局模拟里一次都没跑过，而**回归照样 438/438 全绿**。
⚠️ 与上一轮「bot 不建奇观」的区别：这回**它已经在候选清单里**（`wantWonder` 遍历
`SB.WONDERS`），只是被材料饿死 ⇒ 修法是 `wantBeam` 的阈值改成取「待建奇观要多少」
（结构问题，属覆盖），不是调常数。
⚠️ 但修完之后大图书馆会真的建成 ⇒ 提前拿到 +1000 科技点与图书馆虚级 ⇒
**单局时长会动**。⇒ 属标定，等用户拍，不许我顺手改。

## 五点十一、造价与删除的四个坑（2026-09-28 用户改价 + 删礁石平台）

**判据一（工具层，本仓最贵的一条）：同一文件的多处修改「并行下发」⇒ 先写的那次静默丢失。**
实测：一轮里对 `config.js` 发了 4 组并行 Edit，其中 **3 组的第一条没落盘**
（`wonder_great_lighthouse` 的 cost、`institute` 的 cost、三条注释），
而每一次 Edit **都回了「成功」**，回归也照样 438/438 全绿 ——
因为没有任何断言钉这两处造价，而注释本就不参与断言。
⇒ 判据：**同一文件的多处修改必须串行下发**（一次一条，等回执再发下一条）；
改完必须**回盘 grep 终值**才允许说「改好了」，不许拿 Edit 的成功回执当证据。
⚠️ 这是本项目见过唯一一种「代码改了但代码没改、且所有自动化手段都看不出来」的事故形态。
本次是靠「上屏探针印出的成本串里有两个旧值」抓到的 —— 校验要挑**印得出终值**的手段。

**判据二：删掉一座建筑，必须同时删它的系数键，否则留下死键。**
删礁石平台连带删 `BLD.reefMul`（唯一读取者 `economy.gatherMul`）。
留着不报错、不 NaN，但下一个人会以为「采集倍率通道还在、只是建筑没建」。
**同源风险（更隐蔽）：夹具还在，而力已经不作用了。**
e2e 那条「市政点不吃采集倍率」原先拿 `g1.lvl.reef = 3` 当施力点 ——
建筑删掉后它**恒为 0、恒绿**，成了空跑。
⇒ 换载体时必须**顺便证明载体真的有效**（现改用 `perk.gather`，并断言
`gatherMul(g1) > gatherMul(g0)`）；否则「绿」分不清是「对了」还是「没测」。

**判据三：成本跨过仓储上限 = 静默锁死，既不是 bug 也不报错。**
用户给的大灯塔原 `精铁 500`（大图书馆已在 2026-09-29 改成吃 `铁制支架 50 + 绳 50`；大灯塔同日在 2026-09-29 也撤掉裸精铁，改吃 `硬化珊瑚 50`）。
era2 两座奇观现在都不吃裸精铁，精铁只剩熔炉/铁制支架加工线用。`costOf` / `canAfford` 的撞车风险已随这次改价解除。
⇒ 任何 > CAP_BASE 的成本，**必须显式写出「靠哪几级压舱仓才够得着」**；
调上限与调成本只改一边就会锁死。已在 config 两处注明，等用户对账。

**判据四：删「承重节点」前必须查三样 —— 本轮三个候选各中一样。**

| 候选 | 它承的是什么重 | 查法 |
|---|---|---|
| 热泉井 `geyser` | **地热的唯一产出口**（`fuelRate = lvl.geyser × BLD.fuel × jobs.craft`），而地热是破冰祭坛的唯一燃料 ⇒ 删了终局一秒都开不了 | grep 该**资源**的全部产出算式，看还有没有第二个来源 |
| 匠作 `craftT` | **匠人职业的唯一解锁口**（`eff.unlockJob`，folk.js 反查建表），而匠人是地热算式里的一项 ⇒ 删了 `s.jobs.craft` 恒 0 ⇒ 地热同样归零 | grep `unlockJob`，看该职业还有没有别的解锁者 |
| 通识 `loreway` | **大图书馆的 `need`**（奇观表里 `need` 是科技 id，不是建筑 id）⇒ 删了 need 悬空、奇观静默建不起来 | grep 该 id 的**全部**引用，逐个分清是「读它」还是「写它」 |

⇒ 通用判据：**「它是不是某个东西的唯一来源」**——唯一产出口 / 唯一解锁口 / 唯一引用目标，
三样都查过才允许删。三条的失败形态完全一样：**不报错、不 NaN，只是那条链再也不动。**

它变 0 会把「进下一纪元」变成零门槛空条件，玩家连纪元二的内容都来不及玩。
（`tech.advanceEra` 那条 `p.done` 无法区分「全清了」和「一本账也没有」。）

⇒ **新机制 `pending(name, reason)`（与 `defer` 是两回事，别混用）**：

`pending` = **被测的性质在当前设计下不可能成立**，只能挂起 + 写死理由，**绝不能改断言迁就现状**。

本轮 8 条走了这条路。⚠️ 恒真断言是本轮顺手抓出的另一类垃圾：
`check('破冰结算面板弹出', true)` 写死 true = 永远绿，而它所在的 `if` 分支靠
`!modal.classList.contains('hidden')` 进 —— modal 可能是**前面用例的残留**，
于是「测破冰结算」实际测的是「有个弹窗没收」。断言必须钉住**结果**（`run.broken`），不是钉住**环境**。

⇒ **顺手修掉的真 bug：`workshop.wonderBlocked` 少了一层 `w.need &&` 判据。**
另外三处同级 need 门（`c.need` / `u.need` / `t.need`）都带了判据，只有奇观这处漏了
⇒ `s.techs[undefined]` 恒 falsy ⇒ **没有 need 的奇观被判成「需要先研究『undefined』」凭空锁死**，
而真正拦着的是成本。⇒ 教训：**「字段可缺省」的实现必须写 `if (x.need && …)`，
只写 `if (!s.techs[x.need])` 等于给缺省字段造了一道永假门。**

## 五点十三、第二张横卷：市政树的滚动重置（2026-09-28 用户报）

**症状**：「市政树界面和之前科技树界面一样，固定时间会被拉到最左边。」
**根因与科技树那次一模一样**：`game.js` 的 `PANE_REFRESH = 2000`（**墙钟**）每 2 秒
调一次 `render.renderPanes()`，它把**所有** pane 的 innerHTML 整块重写——
科技树当初修的「先读后写 + 模块记一份 + civicShown/techShown 区分可见态」
只护了 `techScroll` 一家，后加的市政树（`civicScroll`）没人管。

⇒ **判据：横卷类 UI 的滚动留存是「每新增一张卷就要重付一次」的账，不是一次性的修复。**
「容器带 id」只是接头（契约断言钉得住）；「先读后写」的行为本身要模块里配对出现。
新加一张横卷时，`renderPanes` 里的读写对必须**同步加一对**，否则就是用户已报过两次的
同一个 bug 的第三次。

⇒ **验证手段的边界（重申并实测）**：vm 假 DOM 的 `getElementById` 是记忆化的，
桩对象跨 innerHTML 重画存活 ⇒ 行为断言**恒真**，vm 里测不出这个 bug。
本轮用真实 Chrome 注入页（iframe + 同源操作）做确定性复现：
设 `scrollLeft = 300` → 手动 `renderPanes()`（= PANE_REFRESH 做的事）→ 重读。
PASS：300 → 300 → 300（切页签往返也保住）；科技卷对照 250 同路径保住。
⚠️ 探针自己的一个坑：重画后**必须重新 `getElementById` 再读**——旧元素引用已脱离 DOM，
`scrollLeft` 恒 0，拿它当读数会得出假 FAIL（本轮先踩了一脚）。

## 五点十四、信仰全产加成的反自指纪律（2026-09-28）

**设计**：信仰存量按对数刻度给「全产加成」（`faithAllMul`：10→+1% / 100→+2% / 1000→+3%），进入 `globalMul`）
⇒ 珊瑚/石头/金属/暖石/精铁/科技/市政/藻食/地热/奢侈品都被推高。

**判据（反自指 · 会静默自激）**：`faithRate`（信仰自身基础产出 = 人口×0.02×神庙乘区）**绝不调 `globalMul`**。
若它调了，信仰产出被自己的全产加成放大 ⇒ 信仰涨 → 加成涨 → 信仰更快涨 的**正反馈**，指数爆炸且不报错。
这条轴与 `faithMul`（神庙乘区，作用于产出**速率**）是两条独立线，别混。
⇒ 通用判据：**「全产加成」类乘区，若某资源自身也有基础产出，那条产出函数必须绕开该乘区**——
    要么像本作把产出函数写在 globalMul 之外，要么在 globalMul 里对「正在算的资源」特判跳过。

**判据（刻度 · 浮点边界）**：对数刻度用 `Math.floor(Math.log10(faith) + 1e-9)`，**必须 +ε**，
否则 `Math.log10(1000)` 偶发 2.9999999 ⇒ floor=2 ⇒ 1000 信仰只给 +2% 而非 +3%（静默少一档，且只有到 1000 才暴露）。

**判据（面板 gate 读什么）**：「神学完成后才显示信仰面板」的 gate 读 `s.civics.theology`
（市政完成标记），不是 `s.techs`、也不是 `s.lvl.temple`——信仰资源的解锁权写在市政身上（与神庙同规矩）。
渲染层（renderRes）漏这层 gate 会让玩家在神学前就看到一条恒为 0 的信仰行，误以为系统已开。

## 五点十五、陆地贸易 / 幸福度恒温器（2026-09-28 落地）

**设计**：幸福度 `H` 是民生轴（与信仰的「增益条」正交，是「断了就崩」的维护条）。
消耗面：每人每秒烧 `happyCost(H)` 奢侈品（H 越高越贵），给此前零消费端的 `luxury` 一个真实 sink。
效果面：台阶式全产乘区 `happyMul`（动荡<−1→×0.80 / 不满→×0.92 / 安定→×1.00 / 愉悦→×1.05 / 欢欣→×1.10 / 欣喜若狂≥3→×1.20），**排除 luxury 自身**。

**判据一（无贸易中性，会静默惩罚）**：商人产能 `S = merchant×UNIT.luxury×baseMul ≤ 0`（没研究《对外贸易》/ 没雇商人）时 `H` 必须锁定 0（安定，全产不惩罚）。
否则一开局就凭空 −20% 全产，而玩家从没搞过贸易、看不到原因。与「神学前 faith 不生效」同源：系统不存在时轴应中性。

**判据二（恒温器必须用「产能 S」而非「实际烧掉量」，否则永远升不到正档）**：
第一版写成 `supply = 实际烧掉量 = min(库存, 需求×dt)` ⇒ `supply−demand ≤ 0` 恒成立 ⇒ `dH = K·(supply−demand)` 永远只掉不升，H 数学上到不了正档（欢欣/欣喜若狂 成死档）。
正确：`supply = 商人产能 S`，`dH = K·(S − D)`（`D = pop·happyCost(H)`），自动收敛到均衡 `H*`（`pop·cost(H*)=S`）。

**判据三（排除 luxury 自激，与 §五点十四 同一条纪律）**：`happyMul` 不放大 `luxury` 产出，否则
幸福高 → luxury 多 → 幸福更高 正反馈 runaway。实现：拆 `baseMul`（灯塔×信仰，不含 happy）+ `globalMul = baseMul×happyMul`；
`luxury` 产出行走 `baseMul`，其余产出行走 `globalMul`。`rates.luxury` 同式（`S − min(S,D)`）。

**判据四（6 档可达性，先证数学再落地）**：`HAPPY_COST_BASE=0.005`（÷10 锚点对齐 `UNIT.luxury=0.05/商人/s`）、
`HAPPY_COST_SLOPE=0.010`（3× 跨度：H=1→0.015）。均衡 `M/P = cost(H*)/0.05`：
安定 H=1→**30%** 商人、愉悦 H=2→**50%**、欢欣 H=3→**70%**、欣喜若狂 H≥3→**90%**（H≈19.5 触顶，不可超）。
`HAPPY_FLOOR=−2`（动荡档=[−2,−1) 才不落空）。6 档全可达，越高越贵，treadmill 成立。

**判据五（tick 与 rates 同式在动态量上的边界）**：H 随贸易充足度漂移，1 秒内 tick 累积与
`rates()`（用末 H）有微差，属「面板显示当前速率」非撒谎。e2e 改用两条精确不变量钉它：
① `rates.luxury` 公式 = `产能 − min(产能,需求)`（1e-9）；② tick 1 秒净增量 ∈ (0, 产能)（证明确有产出与消耗）。
不再钉 `tick==rates` 精确（恒温器本质：贸易充足时 H 必升，无法在 1 秒内严格稳定）。

**数值已定案（2026-09-29 用户拍板「开始实装」，不再是草案）**：`HAPPY_K=0.02`（收敛快慢）、
6 档乘区（×0.80/0.92/1.00/1.05/1.10/1.20）。再调 = 新一轮标定，须用户重拍。
同日定案的还有 era2 市政 cost（250/300/600/500）。

## 五点二十、热液能重设计为 flow（电力）模型（2026-10-05 用户拍板）

**判据一（「不被储存」是结构要求，不是文案）**：改之前热液能是**会攒的库存池**
（`s.res.hydro += 汽轮机产出` / `-= 工坊与钻机消耗`）⇒「建汽轮机 → +1/s 永久灌进库存」。
用户要的是**电力式瞬态流**：每 tick 产、当场被吃、**不跨 tick 累积**。
⇒ 判据：把某资源从「池子」改成「流」时，先 grep 它**所有 `+=` / `-=` 存量写点**；
有一处 `+=` 就说明它还是池子，需求没被满足。**这类改动不能只改 desc 文案**。

**判据二（瞬态/流量类资源：主数存「每秒」，不是「这 tick」）**：
`s.res.hydro` 初版存了 `hydroAlloc(...).supply`，而 `supply` **已乘 dt**（是「这 tick 产多少」）
⇒ 顶栏主数显示 `0.3` 而不是 `3`。
⚠️ **vm 里的断言全用 `dt=1`，看不出这个错**（只有上屏看 `data-raw` 才抓到）。
⇒ 流量类资源一律存 **÷dt 归一的每秒速率**，并加一条断言「dt=0.1 与 dt=1 同值」钉死。
⇒ **判据：任何「主数 = 每秒 X」的资源，`data-raw` 是上屏验量纲的最后一关。**

**判据三（flow 资源的 rate 语义与存量资源相反）**：顶栏 `rate` 的渲染约定是
「r>0 ⇒ 加 '+' 并染绿、r<0 ⇒ 染红」（`renderRes`）。存量资源传净涨落；**flow 资源要传被吃掉的量并取负**
（`hydro = -(shopDraw + skyDraw)`），否则「热液能被消耗 2/s」会显示成绿色 `+2.00/s`（方向反了）。
⇒ 在 `RESS` 上加 **`flow:true`** 标记，别靠「这个键恰好是消耗」这种隐式约定。

**判据四（分配优先级：读 `skyDraw`，别读 `left`）**：多个消费者共享一条流时，
单一权威分配函数（`hydroAlloc`）要**一次性把每个消费者的份额都算完**，
下游（shell 的天穹钻机）只读 `HF.skyDraw > 0` 判「有没有分到我」。
⚠️ 坑：`left` 是**扣掉钻机那一份之后**的余量（剩 3 < 需求 20），读它会永远判供给不足。
⇒ **判据：分配函数的返回里，每个消费者只认「分给自己的那一份」，不认「别人剩下的」。**

**判据五（奇观 id 与读取键对不上 = 静默死代码）**：本轮挖出**天穹钻机奇观自诞生起从未生效**——
奇观 id 是 `wonder_skydrill`（`buildWonder` 写 `s.wonders['wonder_skydrill']`），
但**全部 4 个运行时读点**写的是 `owned(s).skydrill` ⇒ 恒 `undefined` ⇒ 削壳、市政 +100、幸福度 −1 全是死的。
（`skydrill` 恰好是**纪元五科技**的 key，两套命名空间撞名，抄错也不报错。）
⇒ **grep 奇观 id（`id: 'wonder_x'`）与所有 `owned(s).x` / `s.wonders[...]` 读点，逐一比对字面量。**
⇒ 这类 bug **断言测不出来**：state 里摆 `s.wonders[id]=true` 的测试全绿，而真实路径恒不进那个分支。

**回归全绿 661/661**（新增 9 条 flow 不变量：不累积 / dt 归一 / 工坊优先 / 钻机吃剩流 / 够与不够两种停摆）；
headless Chrome 上屏确认 `热液能 3.0 -2.00/s`（供给 3、消耗 2 红字）与钢 `0.8 +0.09/s`（存量净值绿字）语义分离。
⚠️ 上屏取证**不能用 iframe**（`--dump-dom` 只 dump 顶层文档，iframe 内容抓不到）——
照 `_faith_harness.html` 那样从 index.html 派生整页 + 尾部注入；探针路径要把 `src/`、`css/` 绝对化。
