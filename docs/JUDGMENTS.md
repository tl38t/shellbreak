## 三、UI / 断言 / 渲染反模式

- ⚠️ **`SB.game.render()` 是脏标记门控的**（`game.js:126` `if (dirty)`）：测试里连着调两次
  `render()`，第二次**整帧不跑**，量没刷上去是测试的锅不是产品的锅 —— 中间要补 `markDirty()`。
  真实游戏走 `renderTick()`，不受 dirty 影响。
- ⚠️ **每帧刷新的容器里放按钮**：`input.js` 是 document 级委托（直读 `e.target.dataset`），

  正解 = 状态签名节流（签名只装开关/季节这类低频量，读数走 `textContent` 单独刷 —— 并回签名会让
  按钮每秒重建 10 次）。本作例子见 `renderWarm` / `#envWarm`。
  闸判据 `season(t).mult < 1`，不写死季名/季数。e2e 那条「只扣一次」**必须站在寒流季问**，
  站暖流季会假绿（一口没烧 ≠ 只扣一次）。周期完整口径见 `docs/CURRENT_FACTS.md`。
- ⚠️ **暖石两个出口**（用户拍板）：一份燃烧同时喂「季节减产顶回」与「冻伤减免」；e2e 用「一份暖石只扣一次」钉住。

  ⚠️ **开关位置**：2026-09-27 从巢穴页搬到顶部自然环境卡的 `#envWarm`（看天候才有用，
  摆在建造成群里没人会想到翻）。判「哪张卡能放按钮」先看那容器**是否逐帧重建**。

- ⚠️ **「一次性免费」必须由一次性标记记录，不能靠「当前状态是否为空」推断**（2026-09-27 市政换卡踩到）：

  正解 = `s.cardEver` 一次性布尔，**只置位、不清零**（`setCard` 在真装填时置位）。
  ⇒ **判据：凡是「只允许发生一次」的免费/赠送，问它记在哪 —— 若答案是「看某个当前态」，就是漏洞。**

- ⚠️ **加一条「新产出线」（新资源 / 新职业）的连锁清单**（2026-09-27 加市政点时逐条踩过）：

  ⑦ **`sim/e2e.mjs` 的 bot 权重表**（第三份硬编码表）与其建造清单。
  ⇒ **判据：新产出线跑完全局后 `s.got[新资源] === 0` ⇒ 先去 ④ 和 ⑦ 找，别怀疑公式。**

  ⇒ **判据：共用 CSS 类的东西，一律从事件目标 `closest()` 解析容器，不许按 id 全局取。**
  同类：`render.js` 的 scrollLeft 留存也按 id 取（那个是各自独立的 state，安全）。
- ⚠️ **同一个对象在不同层的名字不同 ⇒ 传参传错会静默走 default 分支**（2026-09-27 踩到）：

  ⇒ **判据：凡「传 item 还是传 item 的子字段」会决定结果的地方，公开 API 收 item、
  内部函数收子字段，且参数名必须区分（`c` vs `cond`）。**
  ⇒ 附带：`condShort` 返回的 `now` **可以大于 `need`**，原始读数不能直接上屏。

### ⚠️ 2026-09-28：一处少括号，把整条资源线的容量打成了 0

**现象**：`--balance` 报「单局 0.00h」、`runHours` 恒 0；e2e 15 项珊瑚链全红；
手动点 600 下「采珊瑚」仍攒到 0.0（需 10）。

**根因**（`src/economy.js` 的 `capOf`，我上轮加奇观仓储时写成）：

```js
return base + (s.lvl.ballast || 0) * BLD.ballastCap +
  SB.wonder ? SB.wonder.matMaxBonus(s, k) : 0;   // ← 少了括号
```

`+` 的优先级高于 `?:` ⇒ 它被解析成 `(base + ballast*cap + SB.wonder) ? bonus : 0`
—— **左半边整个变成条件，返回值只剩三元那一项**。
⇒ `capOf` 对一切非 kelp 资源恒等于「奇观加成」（0 或 200），`CAP_BASE` 与压舱仓全被丢掉。
实测：`capOf(kelp)=200` 对，`capOf(coral)=0`、`capOf(stone)=0` ⇒ 珊瑚/石头/金属/精铁
**全都存不进去** ⇒ bot 跑不穿整局 ⇒ 所有时长数字都是 0。

**为什么断言没抓住**（两条，都要记住）：
1. 石梁那条测的是 `stoneBeam`——它走 `CAP_BASE` 无键 ⇒ `Infinity` 路径，**压根没碰这条 return**；
2. 「仓储加成 +200」比的是**差值**，两边一起错时差值照样成立 ⇒ 假绿。
   ⇒ **判据：凡是「表 + 加成」形状的函数，必须逐键钉绝对值，不能只比差值。**
   已补断言「每种材料的容量都拿得到 CAP_BASE」。

**取证顺序（这次的弯路，下次直接走）**：
`直接调 addRes` → `同 state` → `capOf 各资源` → **把函数体 `toString()` 打印出来** → 看 return 那行。
⚠️ 前四步全都在「推理」，只有打印 `toString()` 才是**看着真实执行的那行代码**。
这次卡在第五条才看见 `+` 和 `?:` 的优先级之争。
⚠️ `capOf.toString().slice(0,300)` **会把 return 截掉**——函数不是从开头到某个点结束的，
截断有可能正好切掉出问题的那几行。**打印全文。**

### ⚠️ 2026-09-28：**墙钟没被钉住**，量具本身在抖（钉随机源不够）

**现象**：钉了 `SB.rng` 之后，同一个仓库连跑三次，整局 **8.49h / 9.69h / 9.97h**，
整棵树 **8.02h / 8.92h / 8.69h**。**同代码、同种子，差 1.5h**——比上次那条还难查，
因为随机数看起来已经「修好了」。

**根因在 `src/game.js` 的 `loop()`**：每帧做两件独立的事——
`var wall = Date.now()` 算 `gap = wall - loop._lastWall`，而 `gap >= CFG.OFFLINE_MIN`
时会调 `planCatchUp` ⇒ 进去是 `drainCatchUp(预算)`，
**那个 while 循环的条件是 `Date.now() - t0 < budgetMs`——墙钟预算**。

sandbox 里 `performance.now` 传的是 `fakeNow`（跟着 `frames()` 一起走），
但 `Date` 传的是**真实 Date**。于是 e2e 跑得越快 gap 越小、越慢就越大，
**离线补算的迭代次数直接由机器负载决定**。这不是误差，是量具 itself 在抖。

**判据（一句话）**：**随机源只是一条输入。时钟是另一条。** 核算前先把
`Date.now` 也接到 `fakeNow` 上（sandbox 里塞一个 `new Proxy(Date, {get:(t,k)=> k==='now'?(()=>fakeNow):t[k]})`），
否则「可复现」只是假象——种子钉住了，机器负载还在顶。
⚠️ ⚠️ 这条**不要擅自加进 e2e**：核算段是用户的活，量具改不动手，等他发话。

## 五点六、全资源产出乘区 `globalMul`（2026-09-28 灯塔上线，四条判据）

1. **`globalMul` 与 `gatherMul` 不是一回事，别合并。** gatherMul 是**采集**倍率，只罩
   珊瑚/石头/金属/暖石四种职业采集物；「全资源 +1%」罩的是**进资源池的每一条产出行**。
   合并的后果是「面板写了 +1%，实际只有四种资源吃到了」。
   **覆盖清单**（新增一种资源进池时必须同步加，漏了不报错不 NaN，只是它静默不吃加成）：
   珊瑚·石头·金属·暖石·精铁·科技·地热·藻食·市政点。
   **例外只有两处，都是有意的**：① 口粮消耗 `foodUse` 不乘（消耗不是产出）；
   ② 精铁的 `fc` —— 乘，但「扣原料那一份」不乘（灯塔不该让玩家少扣一份料）。
2. **乘区宿主 `wonder.globalBonus()` 必须是空实现但存在。** 它现在没有奇观用这个键，
   但留着 = 把「奇观给全资源产出」那条通道事先接通；等将来加键时再补实现，
   就会重演「数据写了实现层没读」的静默断链。
3. **造测试 state 的三个坑**（本轮四条断言全是假红才逼出来的）：
   ① `jobs` / `lvl` 一律 `Object.assign` 打补丁，**禁止整体替换** —— 替换会顺手删掉
      `lvl.reef` 之类没写在字面量里的键，而 `gatherMul` 会读它 ⇒ `undefined * 0.08 = NaN`
      ⇒ 四条采集物静默 NaN；
   ② `frozen` 要显式解掉，冰封期 `cold=0`，产出恒 0 ⇒ 比值无从比；
   ③ 库存初值必须**低于仓储上限**（silt 基础上限 200，填 500 会被 `addRes` 夹回去，
      那一 tick 的主导量变成「削减库存」而不是「产出」，比值完全失真）。
4. **验净额时的「毛额」口径**：silt / warmstone 的 `rates` 是**净额**，末尾减了**未放大**的
   `fc`。补回去的那份必须是**未放大的 fc**（= A 组 iron），拿 `r1.iron`（已 ×1.01）去补
   会重复计价，把正确的 1.010000 虚报成 1.012222 —— **红是假的，会把排查方向带歪**。
   同理，地热那条：灯塔自己也是建筑，升一级会把 `lvlSum` 抬高 ⇒ 城邦维护多 `BLD.upkeep`
   一份也不放大，严格等式是 `fuelRate(B) === (fuelRate(A) − BLD.upkeep) × gm`，
   写成「增量 = 1% × 净额」会红（差 0.0015×gm）。
   ⚠️ 这类「假红」比「不红」更危险：它让人以为产品代码漏乘，去改根本没坏的那一行。

## 五点七、era2 第三层（工程学 / 数学 / 构架术）并存的四种断链（2026-09-28）

三条新科技同时开的三条新通道（配方解锁门、仓储乘区、工坊效率加区），
一次暴露出**四种**「不报错但等于没做」。改任何一条新轴之前都先读这节。

1. **`freshRun` 的 `res` 字面量漏键 ⇒ 产物变 NaN（不报错）**
   加资源只往 `SB.RESS` 加条目、没改 `state.js` 里那行手写字面量 ⇒
   `res.ironBracket === undefined` ⇒ `addRes` 里 `undefined + 5.25 = NaN` ⇒
   `Math.min(Infinity, NaN)` **还是 NaN** ⇒ 产物进了池子却读出来是 NaN，
   面板显示「NaN 铁制支架」，升级项扣费 `undefined - 50` 又把池子整个污染。
   **修了两层**：字面量补齐（`state.js` 已经为 stone/warmstone/culture/stoneBeam
   各写过一次同样的注）+ `addRes` 兜底（**只把非数字洗成 0，NaN 原样留下**——
   NaN 的 typeof 就是 'number'，这层拦不住它，于是它会一路红到断言上；
   把 NaN 也洗成 0，就等于同时藏住「变 0」和「变 NaN」两种事故）。
   **判据**：`freshRun().res` 的键必须覆盖 `SB.RESS`，已有常驻断言盯着（缺一个必红）。

2. **同一个量被写了两遍 ⇒ 台账翻倍**
   `craft()` 在调用端又补了一句 `s.got[c.res] += gain`，而 `addRes` 内部已经写过一次
   ⇒ 工艺制品的累计产出**记了两遍**（实测造一次得 5.25，台账上是 10.5）。
   `s.got` 正是 `{t:'gathered'}` 尤里卡条件的读端 ⇒ 造 100 条石梁会点亮「累计产出 200」，
   **不报错，就是错**。**判据：一个量只该有一个写点**，别在调用方再补一笔。

3. **加区键进了 `mul()` 却没人读**
   `mul()` 老老实实把 `craftRatio: 0.05` 算进了 `T.craftRatio`，面板也照着显示
   「工艺制作效率 +5%」，但 `workshop.craftRatio()` 那两个来源（工坊等级、奇观）
   **压根没有第三条** ⇒ 研究完什么都没发生。**与 `BLD.workshopCraft` 那次同型**。
   **判据：每加一个 effect 键，先回答「谁在读它」**；答不上来就是还没接线。

4. **系数通了、功能却没入口（本次最隐蔽的一条）**
   `capOf` 那条 `upg_ballast_1` 的 ×1.5 早就是通的、e2e 也绿，但工坊面板上
   **根本没这一块**——玩家点不到，×1.5 等于不存在。缺的是**入口**不是实现。
   **判据：点不到的效果等于没做。**
   ⚠️ 这条与 §三 的「UI 断言」不是一回事：那些是「面板要跟着状态翻」，
   这条是「**一块内容整个缺席**，e2e 只看数据层时完全看不出来」。

**附：断言自己算错量纲（不是实现错）。** 那条「造铁制支架」的断言原本拿
`20 - gain`（产出 5.25）去比铁的余额（投入扣 5 ⇒ 实际 15），永远不成立，
而代码从头到尾是对的。**改常数让断言绿 = 标定（停）；断言比错量 = 量错了（修）.**
分界是「错的那一方是谁」——先确认实现对不对，再动断言。

## 六、沿革（考古用，不进日常路径）

- 中期纪律演化：单局 8-14h 那条断言曾当普通回归项，导致每次改完连跑 e2e 都看到 4.35h 抖动；
  2026-09-27 改用 `defer()` 挂起（默认不计 EXIT，核算时显式 `--balance`）。
- 「标定权在用户」升级路径：从「数值倍率等拍板」→「同日升级为工具级硬禁令」。
- 烧石时机三步（见 §三），最后回到「只在寒流季烧」。
- `thermal` 的 cond 是假瓶颈：实测把暖石上限 20 降到 12，完成时刻纹丝不动（它排在 bronze 之后等队列，
  不是等条件）。**改 cond 前先确认它是不是队列最后一项。**
- e2e 偶发 `EXIT=139`（SIGSEGV，卡在 frame 2000），三次复跑未复现 ⇒ 偶发，非改动引发。
- ~~**e2e 15 项「coral=0」红 = 与本轮改动零因果**~~ ⇒ **2026-09-28 更正：因果搞反了。**
  上一条把根因归给「资源线改造的既有欠账」（即断言该改测藻食），**是错的**。
  真根因是下面那条 `capOf` 缺括号（**同一轮改动引入的**）：非 kelp 资源仓储上限恒 0
  ⇒ 珊瑚存不进去 ⇒ 后面 15 项全塌。修掉那个括号后，**15 项一次全绿，e2e 335/335**，
  不需要动任何断言的目标资源。
  ⚠️ 保留这条更正留痕，因为它示范了一个反复出现的失误模式：**看到 15 项红，先按「资源线口径变了」
  去归因，却没去问「这些数字在数学上可能吗」**——珊瑚上限若真是 0，那点 600 次也该是 0，
