## 0. 结构一句话

**五个纪元 = 一个冰下文明从「捞到什么吃什么」到「造机器凿穿冰壳」的发展史。**
每段换的不是数字变大，是**生产方式的换代**：

```
  采集（吃）  →  留住热（加工）  →  得金属（精铁）  →  借力（地热）  →  造机器凿壳
   暗流纪        冷焰纪           硫泉纪            洋流纪          破壳纪
```

Civ6 从远古到工业是 43 项，我们一对一映射后是 28 项 —— 少的部分不是漏了，是**现经济没有那么多东西可解锁**
（只有 13 建筑 / 4 职业 / 7 资源）。这条偏离见 §5，待用户拍板要不要补。

**每个纪元恰好 2 个关键节点** —— 这不是巧合，是刻意定的规则：

## 2. 纪元一 · 暗流纪（Ancient 远古 · 7 项 · 2 关键）

开局：1 名族民 · 唯一职业「采集者」· 唯一资源「藻食」· 建筑 0 座 · **科技面板不显示**。
本纪元只做两件事：**让玩家有事可做**，**让研究资源上线**。

### 2.1 科研面板的开启（纪元一的开场）

**触发**：建成第 5 座深海藻田（`built kelp n=5`）。
**表现**：全屏叙事弹窗 + 科技 Tab 由灰转亮，面板直接展开在「结绳」上（已掌握）。

> 鲛人将细小坚韧的深海藻类打了个结，「这代表今天，」他说。
> 随后，他又打了第二个结，「这代表明天。」

**这条文案是纯包装**，不承担任何机制：它不是尤里卡条件、不额外揭示别的科技、
不折算研究进度、也不等价于「两个结 = 两项科技」。它只是给「科研面板第一次亮起来」
这个时刻配一段台词。机制的触发点就是上面那一条 `built kelp n=5`，两者同一时刻发生。

弹窗里播报的揭示项**只有结绳这一项**。其余六项此时是否已可见，取决于它们各自的
尤里卡条件（见 2.2 的注）。

**为什么开局不显示**：开局科技收入恒为 0（科技只有「学者职业」与「聆听巢」两个来源，
两者开局都没有），面板挂着一堆点不动的灰色按钮，比不显示更像 bug。
面板不显示 ⇒ 那个按钮根本不出现 ⇒ 这个坑从根上不存在。

### 2.2 七项

| 科技 | 成本 | 尤里卡条件 | 解锁内容 | 关键 |
|---|---|---|---|---|

### 2.7 「巢筑」要不要改成解锁「小木屋」（待用户拍板）

猫国小木屋（`js/buildings.js` 实测原文）：

```js
{ name: "hut", prices: [{wood: 5}], priceRatio: 2.5, defaultUnlockable: true,
  effects: { manpowerMax: 75, maxKittens: 2 } }   // 5 木材 · +2 人口上限 · 开局即可建
```

而我们现有建筑 `nest`「礁口巢」= `cost {kelp:10}` · `ratio 2.5` · 住房 `+2` ——
**与猫国 hut 完全同构**，只差名字与付钱的资源。差别在于：猫国里 hut 是开局白送的
（`defaultUnlockable`），**没有"解锁小木屋"的科技**； ours 的礁口巢同样开局可建。
所以「解锁一个能反复盖的住房」这件事在我们这儿**还没有对应物**。

#### 方案 1 · 礁口巢改叫小木屋，改由「巢筑」解锁（推荐）

- `nest` 改名「小木屋」，`defaultUnlockable: true` → `requiredTech: ['shelter']`，
  注释里对齐猫国 hut（5 wood / ratio 2.5 / maxKittens 2）
- 巢筑 `eff: { house: 2 }` → `{ unlockBuild: ['nest'] }`
- 开局可建从 2 座（藻田 + 小木屋）变成 **1 座（藻田）**
- 改动面：config.js 两行 + techs.js 一行。**无需新建筑 id**

> **为什么几乎零体验损失**：住房上限的绝对底数是 `BLD.houseBase = 6`，
> 礁口巢的 `+2/座` 是它**之上的增量**。开局不盖小木屋，人口照样长到 6 人，
> 断粮照旧、生育照旧，只是少一个早期可选项。
> 唯一破的是 `docs/DESIGN_v0.3.md` §5「开局可建 **2 座**」那条，需同步改文档。

#### 方案 2 · 新增「小木屋」作开局第二座，礁口巢后移由「巢筑」解锁

- 新建筑 `hut`「小木屋」：`cost {kelp: 10}`、`ratio 2.5`、住房 `+2`（照抄猫国数值）、开局可建
- `nest`「礁口巢」保留建造权但改为巢筑解锁，并升级为第二档：住房 `+3`、`ratio 2.0`
- 开局仍是 2 座 ✓（`DESIGN §5` 不破），巢筑解锁的是"更好的房子"
- 改动面：**+1 个建筑 id**，须同步 `config` / `state.freshRun` / `state.migrateRun`
  / `balance.mjs` / `e2e.mjs` 五处（见工程纪律）

#### 取舍

| | 方案 1 | 方案 2 |
|---|---|---|
| 开局可建 | 1 座（藻田） | 2 座（藻田 + 小木屋）✓ 守 `DESIGN §5` |
| 两个住房的区分 | —— | 小木屋便宜 +2 / 礁口巢贵 +3 |
| 玩家会不会困惑 | 小木屋=礁口巢，同一物 | 两个名字两条路，要说清谁便宜谁贵 |
| 改动面 | config 2 行 + techs 1 行 | +1 建筑 id，五处清单 |
| 猫国味 | 直译 hut | 多造一个住房层级 |

**倾向方案 1**：改动最小、语义最干净，而且它顺带消掉 §9 Q4 那条「科技 `unlockBuild`
与建筑 `requiredTech` 重复表达」—— 解锁权归科技，建筑身上不再挂 `requiredTech`。

⚠️ 无论选哪个，`house` 加区（§2.6 那个空效果）都得接线：方案 1 之后只剩「龙骨」
（纪元三关键节点）还在用 `eff.house`，接线后它就是"一次性 +2 住房上限"，
与"建筑持续提供住房"形成一层有趣的搭配。

### 2.4 吞吐闸门（数值，本轮未改）

结绳掌握后学者职业上线，科技从 0 变成正数，但一个学者 = **0.03 科技/秒**（`UNIT.sci`）。
实测自第 5 座藻田起：

| 目标 | 等待 |
|---|---|
| 40 科技（凿珊瑚，纪元一初项） | ~22 分钟 |
| 60 科技（历法） | ~33 分钟 |
| 120 科技 | ~67 分钟 |

即开场许诺之后，玩家要盯着空转等 20 分钟才能研究第一项。三个方向：

| 方案 | 做法 | 效果 |
|---|---|---|
| A 压成本 | 纪元一 40/50/60/70/80 → 25/35/45/55/65 | 初项 ~13 分钟 |
| B 提吞吐 | `UNIT.sci` 0.03 → 0.08 | 40 科技 ~8 分钟，成本不动 |
| C 加快人口 | `GROW_NEED` 100 秒/人 → 45 秒/人 | 学者早点变多个，吞吐自己涨起来 |

**推荐 B + A**：初项 5 分钟内研究完，第一个「研究完成」的正反馈来得够快，
人口涨起来后吞吐自然加速，纪元一落在 60–80 分钟。
属标定（改 config 常数），按纪律**本轮未动**，等统一标定那轮一起做。

### 2.8 住房从「硬上限」改成「软上限」（2026-09-25 已落地）

#### 2.8.1 猫国查证：所谓"只加 1 人口的住房"其实有**两档**

`raw.githubusercontent.com/nuclear-unicorn/kittensgame/master/js/buildings.js` 实测原文：

| 建筑 | 造价 | ratio | maxKittens | 备注 |
|---|---|---|---|---|
| `hut` 小屋 | 木材 ×5 | **2.5** | **+2** | `defaultUnlockable`，开局白送 |
| `logHouse` 木屋 | 木材 ×200 + 矿石 ×250 | **1.15** | **+1** | 后期解锁 |
| `mansion` 大厦 | 钛 ×25 + 板 ×185 + 钢 ×75 | **1.15** | **+1** | 后期解锁 |

三点关键，与"给几个位置"比起来，**ratio 才是猫国住房的动力所在**：

1. **+2 的开局白送、+1 的贵**：住房不是"越高级越好"，而是**分档**。
2. **`ratio 2.5` vs `1.15` 是核心**：ratio 2.5 = 每盖一座涨 2.5 倍，盖两座就贵到盖不动 →
   它是**早期的一次性扩张**；ratio 1.15 = 只有小涨，能持续盖 → 它是**后期的人口引擎**。
   ⇒ 猫国的人口增长其实是**"早期靠稀缺档冲一把、后期靠廉价档慢慢爬"**两条腿。
3. 猫国**没有总人口硬上限**（`maxKittens` 是每座建筑提供的量，盖多少涨多少），
   软性节流来自造价递增 —— **这就是"越来越贵"的猫国原型**。

#### 2.8.2 ⚠️ 硬墙实测：人口撞死在 6，食物白白流走

`economy.js:23,198` 目前是两道硬的：

```js
function houseCap(s) { return BLD.houseBase + s.lvl.nest * BLD.house; }   // 6 + 巢级数×2
...
if (s.res.kelp > CFG.GROW_KEEP && s.pop < houseCap(s)) { ... }
```

实测（全采集极端食物策略，10 小时逻辑时间）：

| | 现状（硬墙） | 拆掉墙（住房无限） |
|---|---|---|
| 到 10 人 | >10h | **0.51h** |
| 到 50 人 | >10h | **1.62h** |
| 到 100 人 | >10h | **3.01h** |
| 到 200 人 | >10h | **5.79h** |
| 终局人口 | **6** | 207 |
| 破壳系数 coef | 2.9 | **9.2** |

> **实测推翻了一条我此前的误判**（2026-09-25 早些时候说的）——
> 我当时说"没有住房上限，玩家堆够食物就能把人口拉到几百，破壳进度直接靠人头推平"。
> **这是错的**：207 人也只把 coef 从 2.9 拉到 9.2，而 28 项科技全掌握那项就有 22.4。
> 人口项 `C.POP × pop^0.62` 是**亚线性**的，且 `C.POP=0.26` 很小 —— 人口推不平破壳。
> ⇒ **拆掉硬墙是安全的**，它不是一个必要的平衡件，纯粹是体验障碍。

硬墙最伤人的地方在上一行表格的左列：人口停在 6，而藻食顶在上限 200 吃不完 ——
玩家看到的是"资源满仓、就是不长人"，没有任何可读的原因。

> **顺带一处文档与代码不一致**：`docs/DESIGN_v0.3.md:163` 写的是「巢窟 nest | 藻食 10 |
> **人口上限 +1** | 开局」，而 config 取的是 `house: 2`。文档从头到尾只设过「住房＝人口上限」
> 这一条机制，从没有"住房越来越贵"这一说 —— **软上限是本次首次提出**。
> 另外 `src/config.js:176-179` 里有一条用户自己写下的注释，判断已经和本小节的结论一致：
> 「把人口上限塞进住房成本里，等于让玩家只能靠『不盖房』来限人口，**那是把设计问题藏起来**。
> 人口上限该由人口自身的食物消耗去卡，住房只负责『够住不够住』。」
> 即：这是修一个早就指出过、代码里却还没改的设计问题。

#### 2.8.3 定案：拥挤惩罚（A 方案，已落地）

用户口径：**"不要卡这个人口上限，就用越来越高的住房价格去卡，越到后面住房就越难升级。"**
于是 `houseCap` 那道 `s.pop < houseCap(s)` 判定整条删掉，换成减速系数：

```js
// src/config.js 新增：CROWD: 0.05
// src/economy.js
function beds(s)  { return s.lvl.nest * BLD.house; }        // 床位，不是人口上限
function growRate(s) { return 1 / (1 + CFG.CROWD * Math.max(0, s.pop - beds(s))); }

if (s.res.kelp > CFG.GROW_KEEP) {
  s._grow += dt * growRate(s);
  if (s._grow >= CFG.GROW_NEED) { s._grow = 0; s.pop++; }
} else s._grow = 0;
```

住房的意义随之改写：**它不提供"位置"，它提供"生育速率"**。人口没有天花板，
超住只让下一胎变慢；唯一的解药是盖房，而住房造价是 ratio 2.5 的指数递增
（第 8 座 6,104 藻食、第 10 座 38,147）⇒ **"越到后面越难升级"由价格承担，不再由"不允许"承担。**

**实测矩阵**（12 小时逻辑时间，全采集策略 + 自动盖房；标尺：28 项科技全掌握的科技项 coef = 22.4）：

| 配置 | 终 pop | 到 25 人 | 到 50 人 | 到 100 人 | 到 200 人 | nest 级数 | coef |
|---|---|---|---|---|---|---|---|
| ~~现状（硬墙）~~ | 12 | >12h | >12h | >12h | >12h | 3 | 3.5 |
| 删墙 + 住房无效应 | 366 | 0.94h | 1.63h | 3.02h | 5.80h | 3 | **16.7** |
| 删墙 + 住房提速 0.25 | 664 | 0.63h | 1.03h | 1.83h | 3.41h | 3 | **22.8** |
| 删墙 + 住房提速 0.60 | 1120 | 0.48h | 0.72h | 1.22h | 2.22h | 3 | **30.3** |
| **拥挤惩罚 k=0.05** ← 采用 | **89** | 1.17h | 2.95h | 9.09h | >12h | 3 | **8.7** |
| 拥挤惩罚 k=0.02 | 140 | 1.03h | 2.16h | 5.45h | >12h | 3 | 10.6 |
| 拥挤惩罚 k=0.10 | 66 | 1.41h | 4.26h | >12h | >12h | 3 | 7.8 |

⚠️ **三个数字决定了为什么只能取 k=0.05，不能更松也不能更紧**：

1. **k=0（等于纯删墙）会架空科技树** —— pop 366、coef 16.7，已经逼近科技项 22.4。
   再叠上住房提速（0.6 档）就是 coef 30.3、pop 1120：破壳不再由科技主导，
   而"科技树是整局骨架"是本次改造的前提，这条不能破。
2. **k 越大越接近原来的硬墙** —— k=0.10 时 12h 只到 66 人，和原来卡死在
   6 人虽不是一个量级，但"100 人之前就基本走不动"的观感回来了。
3. **k=0.05 是"看得见回报、又撞得到天花板"的那一档**：到 50 人要 2.95h（比硬墙的 >12h
   宽松得多），但 100 人之后明显吃力，逼玩家去算"还值不值得盖下一座房"。

**落地后的回归（作为标定债台账，见 §9）**：

| 断言 | 结果 |
|---|---|
| 超住时生育减速但不停摆（不是硬墙） | ✓ growRate=0.667 |
| 床位够用则生育满速 | ✓ |
| 超住状态下人口仍在增长 | ✓ pop 10 → 13 |
| 盖了房生育更快（住房是旋钮不是墙） | ✓ 无房 13 人 vs 有床位 15 人 |
| 旧的人口上限函数已彻底移除 | ✓ `houseCap` 不再导出 |
| `e2e` | **88/89**（仅时长一条红） |
| `balance` | **4/6** |

| | 改前 | 改后 |
|---|---|---|
| `e2e` 单局时长 | 5.68h | **3.86h** |
| `balance` rational | 20.14h | **6.31h**（coef 56.9，峰值族民 82） |
| `balance` rush | 41.24h | **6.51h**（coef 52.3，峰值族民 76） |

拆墙让整局**提速 3 倍以上**（人口活了 ⇒ 采集者多了 ⇒ 食物/科技/精铁全线加速）。
方向是对的，但时长掉出了 8–14h 窗 —— 属标定债，不在本轮改。

| 文件 | 改动 |

#### 2.8.4 配套：住房分两档（照抄猫国的 ratio 分工）· 待定

软上限之后，"每座住房 +2"这个说法要重新定义（它不再提供上限位）。
猫国的两档分工照抄如上（小木屋 `ratio 2.5` 早期冲一把 / 木屋 `ratio 1.15` 后期引擎）。

⚠️ **落地时先只留一档**，但实测暴露出一个问题：

| 造价 ratio | 常规策略终 pop | 狂盖房终 pop | 实际盖到 nest 级数 | coef |
|---|---|---|---|---|
| **2.50（现状）** | 90 | 91 | **3** | 8.8 |
| 1.80 | 92 | 85 | 4–5 | 8.9 |
| 1.40 | 96 | 86 | **7–9** | 8.9 |

> **"狂盖房"也没让人口涨，为什么？** 因为生育门槛是 `res.kelp > GROW_KEEP(20)` ——
> 房子一盖就把藻食花掉了，攒不下口粮反而生不了。这本身是个**合理的取舍**
> （要么花钱扩床位、要么攒着生人，二者不可兼得），也正是"用价格卡人口"想要的张力。
> 但 ratio 2.5 下机器人 12 小时只盖得起 **3 座**，住房事实上是一座**够不着的死建筑**。

⇒ **如果要让住房成为真旋钮，就得给它加一档便宜的**（`ratio 1.15~1.40` 的"木屋"），
照抄猫国那条"早期靠稀缺档冲一把、后期靠廉价档慢慢爬"的两条腿结构。
代价是**新增一个建筑 id**，须同步 `config` / `state.freshRun` / `migrateRun` /
`balance.mjs` / `e2e.mjs` 五处（清单见 §2.7 方案 2）。**本轮未做，待用户拍板。**

## 8. 效果词表（eff）

## 10. 依赖深度压平（2026-09-25 落地）

用户拍板 A：把"一根 10 层主干直链"打散成网状。**改的是 reqs 的形状，不是任何数值**。

| | 压平前 | 压平后 |
|---|---|---|

| 最深节点 | `shellBreaker` = L10 | `shellBreaker` = L6 |

各层分布（L0×7 / L1×4 / L2×3 / L3×5 / L4×6 / L5×2 / L6×1）。

**改了哪四处**（都是"换父"，不是"删父"）：

|---|---|---|---|
| 烟囱炉 | 冶炼术 | 匠作 | 它自己只要"热泉炉盖到 2 级"，冶炼术并无顺序上的必需 |

**顺带修掉一个真 bug**：匠作的尤里卡条件原本是"匠人 ≥ 2"，而匠人职业正是它解锁的——
条件要人、人只能靠掌握它才存在，**条件永远不成立**。现在能跑通只因为 `revealEra` 进纪元时
会把旧纪元节点整批强制揭示，把这条自指旁路掉了；那不是修复，只是没触发。
已改为与骨工法同款的"建成骨材工坊"。`sim/e2e.mjs` 新增静态自查，禁止再出现同类自指。

（那是在改终局内容），不是改 reqs 能解决的。

## 11. 两处已定案（2026-09-26 用户拍板）

| 项 | 定案 | 含义 |
|---|---|---|
| **尤里卡折算** | **不折算** | 不做 Civ6 原版「灵光一闪」：条件达成 ⇒ 整项只从「未知」变「可研究」，**不白送任何研究进度**。科技该 40 还是 40。代码里没有任何折算分支（`src/tech.js` 顶部已注明是定案不是待办） |

为什么值得单列：这条是**第二次**拍同一件事（首次见 v0.2 §8）。写进文档是为了防止它以后被
当成"还没做完的功能"顺着补上——补了之后尤里卡就同时是揭示 + 折扣，节奏会整体前移，
而那属于标定，不该在改形状时顺手带进去。

**压深度买到了什么、没买到什么**（免得下次误判）：
`reqs` 只决定"同一层能同时点亮几项"，**不决定研究顺序**——卡节奏的是尤里卡条件，
而纪元闸门（`canStudy` 要求 `tech.era === s.era`）把跨纪元的提前研究也挡掉了。
所以这轮改动**不会让任何科技提前到本纪元之前**，它买来的是同层并行度：
纪元三从"冶炼→烟囱炉→机械"三段排队，变成四项同时可点、第一次出现方向之争。
