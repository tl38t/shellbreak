## 0. 一句话

**功能是树，界面是身体。** 飞升节点仍是 `VEIL_TREE` 表行（前置 / 等级 / 成本 / 重买），但每个节点绑定一个**鲛人器官位**；玩家不是在天赋树上点圆点，而是在一具鲛人底图上**一个器官一个器官地换成机偶**。这正是「插义体」的感觉，也正是「慢慢改造」的爽点来源。

⚠️ 只借《赛博朋克 2077》的**信息架构**，不借它的皮肤。荧光黄 / 洋红 / 扫描线 / 零圆角 / 军事方括号照搬进本作会和深海奇幻割裂——这正是 `parodyband/game-ui-ux` §3 明令禁止的「用霓虹治通用网页设计」。视觉继续用本作成就图标语言 + 硅基材质。

### 1.2 CP2077 义体界面真正值钱的三件事

| 层 | 作用 | 本作对应 |
|---|---|---|
| **身体底图 = 空间锚点** | 把抽象装备栏映射成具身图式，点脑袋 / 点手臂即可定位，不必记分类名 | 鲛人底图 + 器官热区 |
| **分部位插槽 = 兼容容器** | 义体与部位强绑定，列表从源头过滤不兼容项；槽位随进度解锁 | 器官位 + 前置链（第一段生理 → 第二段认知） |
| **容量条 = 全局预算** | 一条进度条汇总所有部位的余量，`已用 / 上限`；槽位管「有没有位置」，容量管「装不装得下」，两道串联闸门 | **改成双读数**：机偶度（进度）+ 热液能常耗（软预算），见 §4 |

CP 的 Cyberware Capacity 是**硬上限**（装不下就置灰）。本作是增量游戏，硬上限会把「慢慢改造」卡成一次性配装；改用**软预算**：安装永远可做，代价是持续上升的热液能常耗，逼玩家先扩热液产能 —— 这是本作现成的资源张力，见 §3.3。

2.0 的 `Full Body Conversion`（每个槽位都装义体才解锁成就）也值得借：**「全身机偶」作为硅基路径的终章节点**，而不是额外成就。

## 4. 双读数（替代 CP 的容量条）

| 读数 | 公式 | 性质 | 界面 |
|---|---|---|---|
| **机偶度** | `已铆接器官数 / 10` | 只涨不退；每重帷幕归零重买 | 顶部主进度条，双色（有机青蓝 → 机偶青绿） |
| **热液能常耗** | `Σ 已铆接器官.hydro` | **软预算**：不阻止安装，持续吃热液网 | 同屏副读数 `+N/s`，与现有热液能收支表并排，不另起一套 UI |

两条必须**同屏**且同源于 `veil.perks`，否则玩家改完一个器官要跳页才知道代价涨了多少（CP 的「闭环决策流」）。改造越多 ⇒ 机偶度越满、热液压力越大，逼玩家回去扩 `robotbay` / 汽轮机产能 —— 这就是「慢慢改造」的长线张力。

## 5. 界面：一具鲛人，不是一屏卡片

### 5.1 布局

```
┌─────────────────────────────────────────────────────────┐
│ 硅基承续   第 K 重帷幕 · 帷幕点余额 · 机偶度 4/10 · +N/s │  ← 状态行，精确数字单独一簇
├──────────────────────────┬──────────────────────────────┤
│  【装配台】              │  【器官详情】                │
│  鲛人底图（300:460，     │   徽记（1:1 成就风格）       │
│  Gemini 素材位）         │   器官名 / 部位 / 阶          │
│  + 10 个可点热区（DOM）  │   状态标签                    │
│  + 左右分列器官清单      │   得到 / 付出 / 前置 / 价格   │
│  已铆接 = 青绿+琥珀+铆条 │   [ 铆接此器官 ]  ← 提交      │
├──────────────────────────┴──────────────────────────────┤
│  全身机偶终章（10/10 才出现）                            │
└─────────────────────────────────────────────────────────┘
```

- **底图是锚点，不是背景板**：器官热区用 DOM 绝对定位覆盖，位置 / 标签 / 状态全可 i18n 且可动态，**任何文字都不烧进图**。
- 点热区或清单项都能选；详情面板恒定在同一位置（空间稳定性）。
- 390px：底图缩到全宽在上，器官清单变 2 列紧凑网格，详情移到下方；状态行 2×2 grid（沿用上一轮 demo 验证过的做法）。

**热区硬判据（本轮 demo 实测抓到的 bug）**：热区是 44px 圆形 `button`，任意两圆**中心距必须 > 44px**，否则窄屏会叠。坐标用容器百分比写死，因此两种屏宽要分别验算：

| 屏宽（headless Chrome `file://` DOM 实测） | `.rig` 实际尺寸 | 最小中心距（B 版） | 判据 |
|---|---|---|---|
| 宽窗口 `--window-size=1400,1000` | **420 × 644** | **64.40px**（02–03） | > 44 ✓ |
| 默认 800 窗口 **与 390px iframe 内** | **330 × 506**（`@media(max-width:820px)` 把 `.rig` 锁在 `max-width:330px`） | **50.60px**（02–03） | > 44 ✓ |
| 最坏保守估算（旧版基线，留作下限） | 323 × 495 | **49.50px**（02–03） | > 44 ✓ |

⚠️ 旧稿写「390px iframe 内 323 × 495」是上一版布局的实测；**本版真实 DOM 实测是 330 × 506**（桌面 800 窗口与 390 iframe 相同），以 `PROBE` 的 `rigW/rigH` 为准。首版坐标把 `08 脑` 与 `07 眼` 摆得过近，整图看不出、裁切放大 1.8× 才发现两圆交叠；且初版只按 330px 宽估算，漏了 `card` 的 14px padding。改过坐标必须重算一次最小间距——不能只凭「看着不挤」。

### 5.4 动效与性能（必须讲透）

60fps = 16.6ms/帧，氛围预算取 1/8 ≈ **2ms**。鲛人底图是静态图，只走 Composite；器官点亮的呼吸环只动 `transform` / `opacity`，合成约 0.02–0.05ms/层，10 层 ≈ 0.5ms，占预算 25%。反过来，一次全屏 `filter: blur()` / `backdrop-filter` 是 4–8ms，一次就爆掉整帧。

机制：Style → Layout → Paint → Composite 五步，只有 `transform` / `opacity` 能跳过 Layout + Paint。所以扫光用 `translateX` 不用 `left`；点亮用 `opacity` 不用 `background-color` 过渡。

边界与失效场景：120Hz 手机上无限 rAF 会跑 120fps（今早星图 iframe 那次是活教材）；thermal throttle 常在 20 分钟后才显形，**前 3 分钟不烫 ≠ 没问题**；10 个半透明发光层叠在底图上吃手机 GPU 带宽；`document.hidden` 要同时停 rAF 与 CSS 动画（`.hidden{display:none}` 只保证前者）。

检查清单：
- [ ] 动效只写 `transform` / `opacity`
- [ ] 循环动效 ≤60fps 钳 + `document.hidden` 守卫 + 切 tab 停 CSS 动画
- [ ] `prefers-reduced-motion` 全停，选中态常驻不靠动画表达
- [ ] 器官状态不每帧重建整页（走 2000ms 壁钟刷新 / 事件驱动）
- [ ] 状态靠文字 + 形状 + 图标三重区分，不只靠颜色
- [ ] 390px 无横拖（`docEl.scrollWidth > clientWidth`）
- [ ] 44px 触区、focus 可见、hover 信息有 ⓘ 等价物
- [ ] 图里零文字，全部文案走 i18n 底表

验收方法：DevTools 录 20s 看 Main 线程与 Composite 层占用；真机挂 20 分钟摸温度；连跑 3 次回归看失败清单 comm（崩溃遍不作结论）。
