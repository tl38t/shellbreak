## 0. 一句话结论

**用两套画种、一套色卡。** 10 枚器官徽记沿用项目里 18 张成就图标的「厚涂发光徽章」；鲛人全身底图用「厚涂奇幻解剖版式（anatomical character plate）」，是第三种画种。两者靠**同一位画师、同一套深蓝黑 + 青蓝 + 琥珀调色、同一种厚涂笔触与光位**统一，而不是硬把 1:1 徽章的「中心对称强符号」套到全身图上。

**「插义体」的感觉从内容来，不从滤镜来**：机械剖面 / 氧化铜 / 黄铜 / 陶钢鳞板 / 铆钉 / 方形插槽 / 液压杆这些**零件语义**，加上上一轮已定的信息架构（身体底图 = 锚点、分部位插槽、软预算双读数）。**不借**荧光黄、扫描线、故障字、军事方括号、等宽微字——那是夜之城的企业终端皮肤，与深海奇幻割裂，也是 `parodyband/game-ui-ux` §3 明令禁止的「用霓虹治通用网页设计」。

## 1. 两个会直接毁掉方案的判断（本轮核出来的）

### 1.1 顺序错了：不能「先定坐标再出图」

`VEIL_SI_ORGAN_SPEC_v0.1.md` §5.1 写「正式底图出图后必须按这 10 个坐标对位」——这个顺序反了。Gemini 每次生成的鲛人姿态、头身比、鳍的位置都会漂，把已锁死的百分比坐标硬贴上去，会出现「脑点到头发、鳃点到肩膀」这种**语义错配**，比上一轮「08 脑 / 07 眼两圆重叠」的几何问题更根本，而且整图看不出来。

**正确顺序：先出构图骨架 → Gemini 按骨架画 → 回来叠坐标核对 → 偏差调坐标，不重出图。**

骨架图由我们程序化生成（`tmp/veil-art/veil-si-rig-guide.png`，900×1380），它精确定义：正面直立、垂直居中、无透视、头颈区占 y 3–25%、躯干 25–50%、鱼尾 50–96%、左右各留约 20% 空。提示词写死「必须严格匹配构图骨架图的姿态、比例、包围盒与解剖标志点相对位置」。

- **只上传 clean 版**（无文字、无编号、无圆点、无标注线、无边框）。`veil-si-rig-align.png` 是叠了 10 个编号圆点的对位版，**只给我们自己和用户核对，绝不上传**，否则 Gemini 会把圆点烧进图里。
- 出图回来把 10 个坐标叠到成图上逐点核对；偏差 ≤8% 就微调 `ORGANS` 表的 x/y 并重算 44px 间距，>8% 才考虑重出。**图服务数据，不是数据服务图。**
- 坐标本来就是「44px 触区间距约束下的近似解剖位」，按骨架图的**部位分组**对位即可（头颈 08/07/01/09 → 躯干 02/03/04/05/10 → 尾 06），不要求毫米级精确。

⚠️ **本节是路线 A 的判据，本轮未采用**。B 路线下 Gemini 成图没有严格匹配骨架（实测头宽仅 15% vs 骨架约 30%，双臂张开到 x 14–86% vs 骨架要求左右各留 20%），旧坐标的 07 眼 / 01 鳃完全落在黑底、10 手擦边。修法不是重出图，而是**按成图逐行亮像素实测重排坐标**：头 `y6–18% / x40–55%`、颈肩 `y22–30% / x32–68%`、臂鳍 `y34–46% / x14–86%`、腹尾 `y50–94% / x30–67%`。⚠️ 44px 圆在 390px 下等于 `x13.6% / y8.9%`，头区 15%×12% 数学上放不下 4 个不重叠圆 ⇒ 01/09 落颈肩、08 压冠鳍尖（半悬空）是几何上限，见 `VEIL_SI_ORGAN_SPEC_v0.1.md` §5.1.1。

### 1.2 画幅错了：规格稿的 3:4 与 demo 容器不一致

| 位置 | 写的画幅 | 实际 |
|---|---|---|
| `VEIL_SI_ORGAN_SPEC_v0.1.md` §7 A | 3:4 竖版 / 落盘 `768×1024` | 比例 0.75 |
| `tmp/veil-organ-demo.html:45` `.rig` | `aspect-ratio:300/460` | 比例 **0.652** |

热区是**容器百分比**定位。图若按 3:4 落盘，`object-fit:cover` 会横向裁掉约 13%，图上每个解剖点的相对 x 全变，上一轮验算出的「390px 最小中心距 49.4px > 44」当场作废。

**修正：落盘画幅必须精确等于容器 = 900×1380（300:460 ×3）。**

- 提示词写「竖版，与上传的构图骨架图完全相同的画幅比例（约 300:460 / 0.652）」，并上传本身就是 900×1380 的骨架图。
- 落盘时用 PIL **`resize` 到精确 900×1380**（允许轻微非等比微调，人物略瘦，风格化鲛人完全可接受），**绝不 `crop`**——裁切会改变解剖点相对位置，缩放是线性映射、百分比坐标零漂移。
- 若要把容器改成 3:4，必须重排坐标：按 390px 实宽 323 / 高 430.7 复算，`02(50,32)–03(50,42)` 中心距只有 **43.1px < 44**，会重叠。所以**不改容器，改画幅**。

## 10. 性能账（必须讲透）

**数字推导**：60fps = 16.6ms/帧，氛围 / 背景预算取 1/8 ≈ **2ms**。纹理内存按 `W×H×3B` 算：底图 900×1380 = **3.73MB**；徽记 512² = **0.79MB/张**，10 张 **7.9MB**。中端手机 JPEG/PNG/WebP 解码约 3–8ms/张（512²）、15–30ms（900×1380），这是**一次性**成本，不是每帧。

若 10 枚徽记同帧解码 = 30–80ms ⇒ 掉 2–5 帧，首屏会肉眼可见地卡一下。所以架构上**清单 chip 用 CSS 圆点、详情卡只显示当前选中的一枚**：首屏实际只解码 2 张（底图 + 1 枚）≈ 18–38ms，分散到两帧内；其余 9 枚 `loading="lazy"` 选中时再取。峰值纹理约 11.6MB，叠加现有双层背景约 21MB ⇒ 约 32MB，中端机可接受但需实测。

**机制**：浏览器 Style → Layout → Paint → Composite 五步。静态 `background-image` 只走 Composite；图片解码发生在 Image decode 阶段，不进每帧。每帧真正的持续成本是 10 个发光热区的 `transform` / `opacity`（合成约 0.02–0.05ms/层 × 10 ≈ **0.5ms**，占 2ms 预算 25%）。反过来一次 1080p 全屏 `filter: blur()` 或 `backdrop-filter` 是 **4–8ms**，一次就爆掉整帧预算 ⇒ 扫光用 `translateX` 不用 `left`，点亮用 `opacity` 不用 `background-color` 过渡。

**代价边界与失效场景**：① 120Hz 手机上无限 rAF 会跑 120fps（今早星图 iframe 那次是活教材，玩家把刷新率调回 60 就退烧，铁证是持续绘制而非加载慢）；② thermal throttle 是累积的，**前 3 分钟不烫 ≠ 没问题**，20 分钟后才显形；③ 10 层半透明发光叠在轮廓上吃手机 GPU 带宽；④ `document.hidden` 要**同时停 rAF 与 CSS animation**（`.hidden{display:none}` 只保证前者）；⑤ 大面积半透明水雾层在低端机比解码更贵。

**检查清单**：

- [ ] 动效只写 `transform` / `opacity`
- [ ] 循环动效 ≤60fps 钳 + `document.hidden` 守卫 + 切 tab 停 CSS animation
- [ ] `prefers-reduced-motion` 全停，选中态常驻不靠动画表达
- [ ] 首屏只解码 2 张图；`decoding="async"` / `loading="lazy"`；图失败有 CSS 兜底
- [ ] 器官状态不每帧重建整页（2000ms 壁钟 / 事件驱动）
- [ ] 六状态靠文字 + 形状 + 图标三重区分，不只靠颜色
- [ ] 44px 触区、focus 可见、hover 信息有 ⓘ 等价物、390px 无横拖
- [ ] 图里零文字，全部文案走 i18n 底表

**验收方法**：DevTools 录 20s 看 Main 线程、Composite 层占用与 Image Decode 尖峰；真机挂 20 分钟摸温度；连跑 3 次回归看失败清单 comm（0xC0000005 崩溃遍不作结论）。
